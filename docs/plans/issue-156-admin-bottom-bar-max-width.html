#156버그 수정

어드민 하단 고정 버튼이 넓은 화면에서 뷰포트 전폭으로 늘어남 — 프레임 폭(max-w-frame) 미적용

damdam6/bernice 브랜치 fix/156-admin-bottom-bar-max-width ← main 라벨 bug 2026-07-28

1요약

어드민 3개 화면(기록지 만들기 · 참가자 추가 · 선수별 입력)의 하단 고정 확인 바가 fixed inset-x-0 셸에 그라데이션 배경·패딩·버튼을 직접 담고 있어, 넓은 화면에서 뷰포트 전폭으로 렌더된다. BottomNav가 #107에서 확립한 "fixed 셸은 위치만 잡는 투명 레이어 + 내용물은 MobileFrame(mx-auto w-full max-w-frame)으로 중앙정렬" 패턴을 그대로 적용한다. 동일한 바 셸 마크업이 세 파일에 문자 그대로 삼중 중복되어 있으므로, 공용 BottomActionBar 컴포넌트로 추출해 한 곳에서 고치고 한 곳에서 테스트한다.

2현황 분석

세 화면 모두 콘텐츠 컬럼은 AdminLayout이 MobileFrame으로 감싸 프레임 폭(src/components/layout/AdminLayout.tsx:8)에 갇히지만, 하단 바는 position: fixed라 프레임 밖으로 탈출한다. 세 곳의 바 셸이 클래스까지 동일한 중복이다:

  • src/pages/admin/CreateSheet.tsx:72 — <div className="fixed inset-x-0 bottom-0 z-10 bg-gradient-to-t from-canvas via-canvas px-4 pt-6 pb-[calc(16px+env(safe-area-inset-bottom))]"> + "N명으로 기록지 만들기" 버튼
  • src/pages/admin/AddPlayers.tsx:111 — 같은 셸 + "N명 추가하기" 버튼
  • src/pages/admin/RecordsPlayerInput.tsx:185 — 같은 셸 + "저장" 버튼

폭 규칙의 정본은 --container-frame: 28rem 토큰(src/index.css:63)이 생성하는 max-w-frame 유틸이고, 유일한 사용 통로가 MobileFrame(src/components/layout/MobileFrame.tsx:8)이다. 선례인 BottomNav(src/components/layout/BottomNav.tsx:23-24)는 fixed inset-x-0 bottom-0 z-10 셸 안에 MobileFrame을 넣고 그 안에 실제 바(border·bg·safe-area)를 두는 구조이며, BottomNav.test.tsx:38-51이 이 3층 구조(바 ≠ fixed → 프레임 클래스 → 바깥 fixed 셸)를 클래스 단위로 검증한다.

3원인 분석

근본 원인 — fixed inset-x-0는 뷰포트 기준 좌우 0 고정이므로 셸 자체가 항상 뷰포트 전폭이다. BottomNav는 셸을 투명 위치 레이어로만 쓰고 내용물을 MobileFrame으로 감싸지만, 세 어드민 화면은 셸에 배경·패딩·버튼을 직접 넣어 폭 제한 계층이 아예 없다(#107 수정 당시 BottomNav만 고치고 어드민 바는 누락). 그 결과 데스크톱에서 콘텐츠 컬럼은 448px인데 버튼은 화면 끝까지 늘어나 PRD(docs/prd-design.html §09 "넓은 화면은 중앙 정렬 폭 제한으로만 대응")와 어긋난다.

수정 형태 — BottomNav와 동형의 3층 구조로 바꾼다. 그라데이션 배경·패딩은 프레임 폭 레이어로 내려간다(BottomNav의 border·bg가 프레임 폭인 것과 동일한 의도 — 바의 시각 요소는 콘텐츠 컬럼과 정렬):

<div className="fixed inset-x-0 bottom-0 z-10">          ← 위치만 잡는 투명 셸
  <MobileFrame>                                          ← mx-auto w-full max-w-frame
    <div className="bg-gradient-to-t from-canvas via-canvas px-4 pt-6
                    pb-[calc(16px+env(safe-area-inset-bottom))]">
      {버튼}
    </div>
  </MobileFrame>
</div>

기각한 대안 — ① 세 파일에 각각 MobileFrame을 인라인 삽입: 동작은 같지만 삼중 중복이 4층 중복으로 커진다. 레포는 최근에도 중복을 공용 유틸로 이관하는 방향(#153·#154)이므로 공용 컴포넌트 추출이 결이 맞다. ② 셸에 max-w-frame mx-auto를 직접 추가: fixed 요소에 inset-x-0과 max-w·mx-auto를 섞으면 동작은 하지만 MobileFrame이 "폭 규칙의 단일 사용처"라는 #107의 계약(MobileFrame.tsx:3-5 주석)을 깨므로 기각.

4작업 단계

  1. 공용 BottomActionBar 컴포넌트 신설 — fixed 투명 셸 + MobileFrame + 그라데이션·safe-area 패딩 레이어를 담고 children으로 버튼을 받는다. BottomNav처럼 #107/#156 패턴 주석을 남긴다. src/components/layout/BottomActionBar.tsx (신규)
  2. BottomActionBar 클래스 검증 테스트 — BottomNav.test.tsx:38-51 스타일로 3층 구조를 검증: 내용물 레이어는 fixed·inset-x-0이 아니고 그라데이션·패딩 클래스를 가진다 / 그 부모 프레임이 mx-auto w-full max-w-frame / 최상위 셸이 fixed inset-x-0 bottom-0. children 렌더도 확인. src/components/layout/BottomActionBar.test.tsx (신규)
  3. 세 화면의 인라인 바 셸을 BottomActionBar로 교체 — 기존 <div className="fixed …"> 래퍼를 제거하고 버튼만 <BottomActionBar>의 children으로 옮긴다. 버튼 자체 클래스·disabled·onClick 로직은 무변경. src/pages/admin/CreateSheet.tsx:72-81, src/pages/admin/AddPlayers.tsx:111-120, src/pages/admin/RecordsPlayerInput.tsx:185-194
  4. 세 화면의 기존 페이지 테스트에 프레임 정렬 회귀 테스트 1건씩 추가 — 확인 버튼의 조상 체인에 max-w-frame 프레임이 있고 그 바깥이 fixed 셸임을 검증(화면이 실제로 BottomActionBar를 쓰는지 가드). src/pages/admin/CreateSheet.test.tsx, src/pages/admin/AddPlayers.test.tsx, src/pages/admin/RecordsPlayerInput.test.tsx
  5. 전체 검증 — 타입체크·전체 테스트를 돌리고, 데스크톱 폭 브라우저에서 세 화면의 바가 콘텐츠 컬럼과 정렬되는지, 모바일 폭(≤448px)에서 기존과 동일한지 눈으로 확인. npm test, tsc, 로컬 dev 서버 ✓ tsc·전체 784 테스트 그린. 육안 확인은 클래스 검증 테스트 4건으로 갈음(#107 BottomNav 수정과 동일 접근 — 어드민 화면은 로그인·시트 API 의존이라 dev 서버 육안 확인은 리뷰 프리뷰에 위임).

5리스크

리스크영향완화책
그라데이션 배경이 프레임 폭으로 줄어 넓은 화면에서 바 좌우 여백에 배경이 없음 낮음 — 콘텐츠 컬럼도 같은 프레임 폭이라 스크롤 콘텐츠가 바 좌우로 지나갈 일이 없고, BottomNav의 border·bg도 이미 프레임 폭 이슈 기대 동작("바 내용물이 프레임 폭 중앙정렬")과 일치함을 플랜에 명시, 브라우저에서 육안 확인
DOM 계층이 한 단계 깊어지며 기존 페이지 테스트의 셀렉터가 흔들릴 가능성 낮음 — 기존 테스트는 role/텍스트 기반 조회라 계층 무관 전체 테스트 스위트 실행으로 확인
모바일 폭(≤448px) 시각 변화 없음이 기대값 — max-w-frame=28rem은 그 폭에서 no-op 완료 조건에 명시, dev 서버 모바일 뷰포트로 확인

  • 기존 동작 무회귀 — npm test 전체 통과(특히 CreateSheet·AddPlayers·RecordsPlayerInput의 기존 선택/제출/토스트 시나리오), tsc 타입체크 통과.
