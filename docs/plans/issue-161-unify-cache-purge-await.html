#161버그 수정

쓰기 후 캐시 무효화 통일 — create-sheet waitUntil→await + purgeRecordsCache 헬퍼

damdam6/bernice 브랜치 fix/161-unify-cache-purge-await ← main 라벨 bug 2026-07-28

1요약

functions/api/admin/create-sheet.ts:92가 records 엣지 캐시 삭제를 context.waitUntil로 미뤄, 201 응답 직후 프론트 refetch가 옛 엣지 캐시를 받을 수 있었다 — docs/prd-record-input.html §09 "무효화는 응답을 돌려주기 전에 await" 위반. 또한 캐시 삭제 호출이 4곳(쓰기 3곳 + refresh.ts)에 흩어져 있고 caches.default.delete 인자 표기도 문자열/new Request(...)로 혼재해 있었다. functions/lib/records-cache.ts에 purgeRecordsCache() 단일 헬퍼를 추가하고 4곳 모두 이를 거치도록 통일했다.

2현황 분석

무효화 호출부 4곳의 기존 상태:

  • functions/api/admin/create-sheet.ts:92 — context.waitUntil(caches.default.delete(new Request(RECORDS_CACHE_KEY))). 응답을 막지 않으려 waitUntil로 넘겨, 삭제 완료 전에 201 응답이 먼저 나갈 수 있었다(PRD §09 위반의 유일한 지점).
  • functions/api/admin/records.ts:126 — 이미 await caches.default.delete(RECORDS_CACHE_KEY)(응답 전 await, 정상).
  • functions/api/admin/add-players.ts:88 — 이미 await caches.default.delete(new Request(RECORDS_CACHE_KEY))(응답 전 await, 정상).
  • functions/api/refresh.ts:8 — const deleted = await caches.default.delete(RECORDS_CACHE_KEY), 결과 boolean을 응답 바디로 그대로 반환.

functions/lib/records-cache.ts는 그동안 RECORDS_CACHE_KEY·RECORDS_CACHE_TTL_SECONDS 상수만 export하고, 삭제 로직 자체(및 new Request(...) 래핑 여부)는 각 호출부가 개별 구현했다. GET 경로(functions/api/records.ts:29)의 context.waitUntil(cache.put(...))는 캐시 "채우기"라 이번 이슈 범위 밖 — 응답을 막을 이유가 없는 정상 패턴이므로 그대로 뒀다.

3설계

records-cache.ts에 export async function purgeRecordsCache(): Promise<boolean>를 추가해 caches.default.delete(new Request(RECORDS_CACHE_KEY))를 캡슐화했다. new Request(...) 래핑 형태로 고정한 이유: add-players.test.ts·create-sheet.test.ts의 기존 캐시 목이 delete(request: Request) 시그니처(호출 인자의 .url을 읽음)를 전제하고 있어, 이 모양을 깨지 않는 쪽이 회귀가 가장 적다. records.ts·refresh.ts는 원래 문자열을 직접 넘겼지만 헬퍼 내부에서 항상 new Request로 감싸므로 동작(삭제 대상 키)은 동일하게 유지된다.

대안으로 "문자열 그대로 넘기는 버전"도 검토했으나, 그러면 add-players.test.ts· create-sheet.test.ts의 기존 fake cache가 깨져(request.url이 undefined) 더 넓은 회귀를 만든다 — 기각.

4작업 단계

  1. records-cache.ts에 purgeRecordsCache(): Promise<boolean> 추가( caches.default.delete(new Request(RECORDS_CACHE_KEY)) 래핑), 헤더 주석을 4개 호출부 수렴 구조로 갱신. functions/lib/records-cache.ts
  2. create-sheet.ts:92 — context.waitUntil(...) 제거 → await purgeRecordsCache()로 교체, 인접 주석(91행)을 "응답 전 await" 근거로 갱신. functions/api/admin/create-sheet.ts
  3. admin/records.ts:126 · add-players.ts:88 · refresh.ts:8를 각각 purgeRecordsCache() 호출로 교체(동작 불변 — 세 곳 모두 이미 응답 전 await였으므로 순서는 그대로). functions/api/admin/records.ts, functions/api/admin/add-players.ts, functions/api/refresh.ts
  4. create-sheet.test.ts: 삭제 어서션을 flush() 없이 onRequestPost 반환 직후로 옮겨 "응답 전 삭제 완료"를 직접 검증. 더는 쓰이지 않는 waitUntilPromises/flush 헬퍼를 makeContext에서 제거. functions/api/admin/create-sheet.test.ts
  5. refresh.test.ts: deleteMock이 문자열이 아닌 Request를 받게 됐으므로 toHaveBeenCalledWith(RECORDS_CACHE_KEY) 대신 .mock.calls[0][0].url 비교로 수정 (계획에 없었지만 헬퍼 통일의 직접 결과 — 이슈 완료 조건엔 명시되지 않았으나 그린 유지에 필수). functions/api/refresh.test.ts 이슈 원문 완료 조건에 없던 파일이지만, purgeRecordsCache 시그니처 통일의 필연적 파급 — 계획 대비 확장.

5리스크

리스크영향완화책
