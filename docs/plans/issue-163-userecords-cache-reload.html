#163버그 수정

useRecords refetch 브라우저 캐시 우회 — queryFn cache:'reload'

damdam6/bernice 브랜치 fix/163-userecords-cache-reload ← main 라벨 bug 2026-07-28

1요약

useRecords.ts:63의 queryFn이 cache 옵션 없이 fetchRecords를 호출해, 브라우저 HTTP 캐시가 응답을 가로챌 수 있다. #151은 새로 고침 버튼(useRefreshRecords.ts)에만 cache:'reload' 우회를 적용했고, 그 외 모든 (재)조회 — 초기 마운트, staleTime 만료, invalidateQueries 후 자동 refetch — 는 여전히 기본 캐시 동작이라 관리자 액션 후에도 최대 6시간(RECORDS_CACHE_TTL_SECONDS) 묵은 브라우저 캐시 응답을 볼 수 있다. queryFn이 항상 cache:'reload'로 호출하도록 바꿔 모든 records 조회가 네트워크(엣지)까지 가게 한다. 서버가 추후 no-store로 전환되면 기능적 no-op이라 비용 없다.

2현황 분석

useRecords.ts:60-67의 useQuery는 queryFn: ({ signal }) => fetchRecords(signal)로 cache 옵션을 넘기지 않는다. fetchRecords(useRecords.ts:10-13)는 받은 cache를 그대로 fetch('/api/records', { signal, cache })에 전달하므로, 여기서는 cache: undefined → 브라우저 기본 HTTP 캐시 동작이 적용된다.

서버(functions/api/records.ts:25-27)는 200 응답에 Cache-Control: public, max-age=${RECORDS_CACHE_TTL_SECONDS}를 붙이고, RECORDS_CACHE_TTL_SECONDS(functions/lib/records-cache.ts:12)는 60*60*6 = 21600초(6시간)다. 즉 한 번 200을 받으면 최대 6시간 동안 브라우저가 네트워크를 타지 않고 자체 캐시로 응답할 수 있다.

#151(커밋 cbab02b)이 도입한 useRefreshRecords.ts:27는 fetchRecords(undefined, 'reload')로 명시적으로 우회를 넘기는 유일한 호출자다 — 순서는 ① /api/refresh POST로 엣지 캐시 퍼지 → ② cache:'reload' refetch → ③ setQueryData. 반면 useRecords() 자체의 queryFn은 그대로다.

결과: 관리자 액션이 RECORDS_QUERY_KEY를 invalidate해도(예: 로그인 성공 후 LoginGate의 invalidateQueries, 또는 기록 저장 후 다른 화면의 invalidate) 그 자동 refetch는 useRecords()의 queryFn을 타므로 여전히 cache 미지정 — 브라우저 HTTP 캐시가 최대 6시간 묵은 응답으로 응답해 무효화 자체가 무력화될 수 있다. 이는 링크된 캐시 무효화 설계 T3(관리자 액션 후 스테일 데이터)의 프론트 측 방어 공백이다.

추가로, 서버가 향후 no-store로 전환되더라도(관련 이슈, 이 작업 범위 밖) 전환 배포 시점 이전에 이미 각 브라우저에 저장된 max-age=21600 엔트리는 HTTP 캐시 규약상 자기 만료 시점까지 유효하다 — 서버 헤더가 바뀐 걸 그 엔트리는 모른다. queryFn이 항상 'reload'를 넘기면 서버 헤더 값과 무관하게 이 전환기 문제도 함께 해소된다.

3원인 분석

근본 원인: useRecords의 queryFn이 #151에서 새로 고침 버튼에만 국한해 넣은 cache:'reload' 우회를, records 쿼리의 일반 (재)조회 경로에는 적용하지 않았다 — 우회가 "명시적으로 새로고침을 누른 경우"로 좁게 스코프됐고, invalidate 기반 자동 refetch는 고려 대상이 아니었다.

수정: useRecords.ts:63의 queryFn을 ({ signal }) => fetchRecords(signal, 'reload')로 바꿔, 이 쿼리의 모든 조회(초기·재조회·invalidate 후 refetch 전부)가 항상 브라우저 HTTP 캐시를 건너뛰게 한다.

기각한 대안

  • staleTime을 낮춰 더 자주 refetch — React Query 캐시 재검증 빈도만 올릴 뿐, fetch 자체가 여전히 cache 미지정이라 브라우저 HTTP 캐시가 그 refetch에도 응답할 수 있다. 근본 원인(HTTP 캐시 우회 부재)을 건드리지 않는다.
  • 커스텀 Cache-Control: no-cache 요청 헤더 추가 — fetch의 표준 cache 옵션이 이미 이 코드베이스의 관례(#151)이고 목적에 정확히 맞는다. 별도 메커니즘을 새로 들이는 것은 불필요한 중복이다.

서버가 no-store로 전환되면(범위 밖) cache:'reload' 지정은 이미 네트워크로 가는 요청에 아무 영향이 없는 기능적 no-op이 되어 유지 비용이 없다.
