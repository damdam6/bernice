P7 — 도메인 타입 개정: endSessionDate · Session.eventKeys (계약 키스톤)

damdam6/bernice 브랜치 feat/110-domain-types-endsessiondate-eventkeys ← main 라벨 enhancement 2026-07-26

1요약

shared/domain.ts에 종목 생애주기 계약을 위한 필드 2개(EventDefinition.endSessionDate, Session.eventKeys)를 신설하고, 완전성·구성 규칙 주석 3곳을 개정한다. 로직 자체는 바꾸지 않지만, 두 필드가 필수이므로 TypeScript 구조적 타이핑상 이 두 타입을 리터럴로 만드는 모든 지점(운영 코드 3곳 + 런타임 검증 1곳 + 테스트 픽스처 다수)이 컴파일 에러로 드러난다. 이 이슈의 실제 작업량 대부분은 그 컴파일 에러를 npm run typecheck가 그린이 될 때까지 기계적으로 메우는 것이고, 값 자체는 오늘 시점의 실제 동작을 그대로 반영하는 값(예: 아직 5열 파싱이 없으니 endSessionDate: null 고정)만 채운다.

2현황 분석

shared/domain.ts:38-45의 EventDefinition과 :64-69의 Session은 각각 종료 회차, 회차별 측정 종목 목록을 표현할 필드가 없다. PRD(docs/prd-event-lifecycle.html §03 D3, §06)가 이 계약 개정을 P7 전체의 유일한 하드 선행으로 지정했다 — 이 타입이 안정되어야 파서(V3 완화·V4 신설)·계산(회차별 순회)·프론트 파생(Wave 1의 9건)이 픽스처 기준으로 병렬 착수 가능해진다.

두 신규 필드를 필수로 추가하면 다음 3개 운영 코드 지점이 즉시 컴파일 에러가 된다(임시로 필드를 추가해 npx tsc -b --force로 실측 확인함):

  • functions/lib/parse-goals.ts:63-70 parseGoalRow() — 목표 탭 4열(종목|목표|만점|방향)만 읽는 현재 파서. 5열(종료 회차) 파싱은 이 이슈 범위 밖(Wave 1 별도 이슈)이므로, 지금은 실제 동작과 일치하는 고정값 endSessionDate: null만 채운다.
  • functions/lib/parse-session.ts:107 parseSession() 반환값 { date: tabName, entries } — 같은 함수 58행에서 이미 mapHeaderToEvents(rows[0], events)로 헤더 순서의 EventColumn[](각 { event, columnIndex })을 계산해두고 있다. eventKeys: eventColumns.map(c => c.event.key)는 이미 계산된 값을 노출하는 것뿐, 새 로직이 아니다. (현재 mapHeaderToEvents는 헤더에 없는 목표 종목이 있으면 즉시 에러를 던지므로(159-162행, V3 완화 전) 지금 시점엔 이 값이 사실상 events[] 전체 key와 항상 같다 — 그래도 계약대로 헤더 순서를 그대로 노출한다.)
  • functions/lib/build-records-response.ts:32-37 excludeWithdrawn() — 탈퇴 선수를 걸러낸 새 Session 리터럴을 만들면서 date·entries만 복사하고 있어(원본 eventKeys가 조용히 유실됨), eventKeys: session.eventKeys를 명시적으로 이어받아야 한다.

src/lib/parse-records-response.ts는 자기 파일 헤더 주석(1-4행)에서 스스로 "조립형이라 domain.ts에 필수 필드가 추가되면 여기가 컴파일 에러로 함께 강제된다"고 명시한 설계다 — parseEventDefinition()(56-72행)과 parseSession()(115-121행)이 정확히 그 지점이다.

반대로 구조 변경이 없는 세 가지 주석 전용 개정(SessionEntry.scores 완전성 계약, SessionRankings.events 구성 규칙, PlayerSummary.trends 보강)은 필드 타입 자체(Record<string, EventScore>, EventRanking[], PlayerEventTrend[])가 그대로라 functions/lib/compute-rankings.ts·functions/lib/player-summary.ts 등 소비 코드는 손대지 않는다 — 실제 필터링 로직 변경(예: computeSessionRankings가 eventKeys만 순회하도록)은 PRD §07이 명시한 대로 Wave 1(파서 V3 완화 이후 이슈)의 몫이다.

3설계

선택한 접근: (a) shared/domain.ts에 두 신규 필드를 추가하고 세 곳 주석을 개정 → (b) 컴파일러가 강제하는 3개 운영 코드 지점 + 1개 런타임 검증 지점을 "오늘 시점 실제 동작과 일치하는" 최소 값으로 메움 → (c) npm run typecheck가 나열하는 나머지 전부(테스트 픽스처)를 기계적으로 메움 → (d) toEqual로 파서 실제 출력과 정확 비교하는 테스트(타입 체커가 못 잡는 런타임 값 불일치) 별도 확인.

기각한 대안: 두 필드를 옵셔널(?:)로 추가 — PRD·이슈 모두 "항상 존재"를 계약으로 명시했고(§06 "eventKeys 신설 — 참가자 0명 회차에서도 측정 종목을 알 수 있도록 명시"), 옵셔널로 두면 하류 소비자가 다시 undefined 분기를 넣어야 해 오히려 Wave 1의 전제(완전성)를 깬다. 컴파일 에러가 늘어나는 비용을 감수하고 필수로 간다.

  5. 프론트 런타임 검증 — 필드 검증·통과 추가 — parseEventDefinition()에 endSessionDate(문자열 또는 null) 검증+통과, parseSession()에 eventKeys(문자열 배열) 검증+통과 추가. 기존 parseArray·isPlainObject 관용구 그대로 재사용. src/lib/parse-records-response.ts:56-72,115-121
