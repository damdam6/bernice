P7 — build-records-response 조립: V6 실존 회차 대조 + eventKeys 배선

damdam6/bernice 브랜치 feat/120-build-records-response-v6-wiring ← main 라벨 enhancement 2026-07-27

1요약

선행 이슈 #111(parse-goals 5열 스키마)·#112(parse-session 매핑 완화)가 이미 병합되어 EventDefinition.endSessionDate와 Session.eventKeys는 조립 단계까지 관통 배선이 끝난 상태다. 남은 것은 PRD docs/prd-event-lifecycle.html §05의 검증 매트릭스 중 유일하게 조립 단계(build-records-response.ts) 몫으로 배정된 V6 — 목표 탭 종료 회차 값이 실제로 존재하는 회차 탭 이름과 일치하는지 대조하는 로직이 아직 없다는 점뿐이다. 이 이슈는 그 V6 검증 함수를 추가하고, 성공/실패 테스트와 혼재 번들(구 회차 + 신규 회차, 서로 다른 eventKeys) 조립 정합성 테스트를 채운다.

2현황 분석

  • functions/lib/parse-goals.ts:19,82,103-110 — 5열 헤더(종목|목표|만점|방향|종료 회차) 엄격 검증과 parseEndSessionDate(V5: 형식·캘린더 검증, isValidRoundTabName 재사용)가 이미 구현·병합됨(#135). 반환 타입은 ParseGoalsResult { events, sheetRowByKey }.
  • functions/lib/parse-session.ts:116,140,175-179 — parseSession이 이미 Session.eventKeys를 헤더 순서로 산출하고, mapHeaderToEvents가 V3(목표 종목 전체 헤더 강제 제거)·V4(종료 회차 초과 회차에 컬럼 존재 시 에러)를 이미 구현함(#112/#133).
  • shared/domain.ts:45,72,148-155 — EventDefinition.endSessionDate, Session.eventKeys, RecordsResponse.events가 이미 타입 계약에 반영돼 있다.
  • functions/lib/build-records-response.ts:49,57-58 — buildRecordsResponse가 이미 const { events } = parseGoals(...)로 새 반환 타입을 받아 parseSession에 넘기고, excludeWithdrawn(:32-38)이 eventKeys를 그대로 통과시킨다 — 즉 "관통 배선" 자체는 완료 상태다.
  • 반면 V6(종료 회차 ↔ 실존 회차 탭 대조)에 해당하는 코드는 어디에도 없다 — build-records-response.ts 전체를 검토했으나 event.endSessionDate를 bundle.rounds와 비교하는 로직이 없다(grep -rn "endSessionDate" functions/lib/build-records-response.ts → excludeWithdrawn의 eventKeys 통과 줄 1건만 매치). PRD §07 표 (docs/prd-event-lifecycle.html:277-279)도 이 배치를 명시한다: "종료 회차 ↔ 실존 회차 탭 대조(V6)를 이 단계에 배치(회차 목록을 아는 유일한 지점)".
  • functions/lib/build-records-response.test.ts는 이미 5열 GOALS_ROWS 픽스처(:13, 종료 회차 빈칸)를 쓰지만 단일 회차 번들만 다루고, V6 성공/실패 케이스도 다중 회차(혼재 eventKeys) 케이스도 없다.
  • 에러 처리 경로 — functions/api/records.ts:36-50의 errorResponse는 RecordsAssemblyError(구조적 사전조건: 탭 자체 누락)는 err.code로, 그 외 일반 Error는 sheet_data_invalid/500으로 매핑한다. V1~V5는 전부 일반 Error를 던진다(parse-goals.ts:112-114, parse-session.ts 각 throw new Error(...)) — RecordsAssemblyErrorCode는 현재 'missing_roster_tab' | 'missing_goals_tab' 두 구조적 케이스만 갖는다.

3설계

채택: buildRecordsResponse 안, parseGoals 직후·세션 파싱 이전에 validateEndSessionDates(events, bundle.rounds) 헬퍼를 호출한다. 헬퍼는 bundle.rounds의 탭 이름 집합을 만들고, endSessionDate !== null인 각 종목에 대해 그 날짜가 집합에 있는지 확인한다. 없으면 종목명·종료 회차 날짜를 담은 메시지로 일반 Error를 던진다 — V1~V5와 동일한 fail-loud 스타일(에러 코드가 아니라 사람이 읽을 메시지로 원인을 특정)을 그대로 잇는다. 위치를 세션 파싱 이전으로 두는 이유는 V6이 "회차 목록을 아는 유일한 지점"(PRD)이라는 원칙을 parseGoals 호출 직후로 가장 좁게 해석하면, 이후 세션 파싱(V4)이나 랭킹 계산이 이미 모순된 endSessionDate를 전제로 작업을 진행하기 전에 즉시 끊어낼 수 있기 때문이다. 두 검증(V4·V6)은 독립적이라 순서 자체가 결과를 바꾸지는 않지만, 더 이른 실패가 디버깅 시 더 명확한 원인을 준다.

기각 — 새 RecordsAssemblyErrorCode 추가: 'unknown_end_session_date' 같은 새 코드를 만들고 RecordsAssemblyError로 던지는 방안도 가능했지만, 기존 RecordsAssemblyErrorCode는 "탭 자체가 없음"이라는 구조적 사전조건 전용으로 쓰이고 있고(functions/api/admin/create-sheet.ts:60,63도 같은 두 코드만 별도 분기), V6은 성격상 V1~V5와 같은 시트 데이터 정합성 오류다. 새 코드를 추가하면 오히려 두 카테고리(사전조건 vs 데이터 정합성)의 경계가 흐려진다. 일반 Error로도 errorResponse가 이미 500 + 메시지로 응답하므로 별도 배선이 필요 없다.

기각 — parseGoals 내부에서 검증: parseGoals는 회차 탭 목록을 모른다(목표 탭 값만 받음). 회차 목록을 인자로 추가로 넘기는 방안은 파서의 단일 책임(목표 탭 파싱)을 흐리고, PRD가 명시적으로 조립 단계를 지정한 이유(§07)와도 어긋난다.

4작업 단계

  1. validateEndSessionDates(events, rounds) 헬퍼를 추가하고 buildRecordsResponse에서 const { events } = parseGoals(...) 바로 다음 줄에서 호출한다. 회차 탭 이름 집합은 new Set(bundle.rounds.map(r => r.name))로 만들고, 매치 실패 시 메시지에 종목 key와 endSessionDate 값을 포함해 "오타이거나 아직 그 회차 탭이 생성되지 않았을 수 있다"는 취지를 안내한다(V4/V5 메시지 톤과 통일). functions/lib/build-records-response.ts
  2. V6 성공/실패/현역(null) 단위 테스트 3건을 추가한다: (a) endSessionDate가 bundle.rounds 중 하나와 일치 → 정상 조립, (b) 존재하지 않는 날짜 → throw + 메시지에 종목명·날짜 포함 검증, (c) endSessionDate: null(현역) → 회차 목록과 무관하게 항상 통과(회귀 방지 — 오탐 없음을 명시적으로 고정). functions/lib/build-records-response.test.ts
  3. 혼재 번들 조립 정합성 테스트를 추가한다 — PRD §10 마이그레이션 시나리오를 축소 재현: 회차 A(과거, 구 종목 헤더 + 그중 하나는 endSessionDate가 회차 A로 종료)와 회차 B(최신, 신규 종목 헤더, 종료 종목 컬럼 없음) 두 개짜리 번들을 조립해 (i) result.events가 목표 탭 행 순서대로 전체(종료 종목 포함) 노출되는지, (ii) result.sessions[0].eventKeys와 result.sessions[1].eventKeys가 각 회차 헤더와 정확히 일치하는지, (iii) V4 위반이 없어 에러 없이 통과하는지를 검증한다. functions/lib/build-records-response.test.ts
  4. npm run test(vitest)와 npm run typecheck(tsc -b)로 전체 회귀 확인 후 커밋. 결과: 83개 파일 716개 테스트 전부 통과, 타입 에러 없음.
