P7 — 기록 입력 화면: 회차별 입력 필드 + 면제 토글 상수 갱신

damdam6/bernice 브랜치 feat/126-input-screen-session-fields-exemptions ← main 라벨 enhancement 2026-07-27

1요약

선수별 입력 화면(RecordsPlayerInput)이 전역 종목 목록 events[] 전체를 렌더해, 과거 회차에 없는(또는 미래에 추가된) 종목 필드까지 노출되는 버그를 고친다. 그 회차 Session.eventKeys만 헤더 순서대로 렌더하도록 바꾸고, 날짜 선택·참가자 목록 화면이 이미 회차 기준 분모로 배선돼 있는지(#117) 확인한다. 마지막으로 면제 토글 노출 종목 상수를 45도패스캐치(종료)에서 후속 종목인 패스 3종(체스트·바운드·원핸드)으로 갱신한다(PRD §09 기본값 제안 채택).

2현황 분석

버그 재현 경로 — src/pages/admin/RecordsPlayerInput.tsx:68에서 PlayerInputContent에 events={data.events}(전역 목표 탭 행 순서, 종료 종목 포함)를 그대로 넘기고, :120의 events.map(...)이 그 배열 전체를 카드로 렌더한다. shared/domain.ts:45-46 계약대로 events[]는 종료 종목까지 포함한 전체 목록이고, 회차별 실측 종목은 Session.eventKeys(shared/domain.ts:72, 헤더 순서)로 별도 존재한다 — 지금 코드는 이 둘을 구분하지 않는다.

결과적으로 과거 4종목 회차(eventKeys = 드리블셔틀런·골밑슛·자유투·45도패스캐치)를 열어도, 전역 events[]에 신규 7종목이 추가된 뒤라면 화면엔 존재하지 않는 종목 카드가 나타난다. 반대로 신규 7종목 회차를 열었을 때 events[] 순서가 회차 헤더 순서와 다르면 카드 배열도 어긋난다.

같은 문제를 이미 올바르게 푼 선례 — src/lib/profile-view.ts:33-37(buildRadarAxes)와 functions/lib/compute-rankings.ts:72-76가 동일 패턴을 쓴다: events[]를 Map<key, EventDefinition>으로 색인한 뒤, session.eventKeys를 순회하며 그 Map에서 찾아 없는 건 걸러낸다(filter(event is EventDefinition => ...)). RecordsPlayerInput도 이 "eventKeys 기준 순회" 패턴을 그대로 재사용한다.

#117(entry-status) 배선 현황 — 이미 완료돼 있다. src/lib/entry-status.ts:15-25는 deriveEntryStatus(entry, eventKeys)·countCompleted(entries, eventKeys) 둘 다 분모를 eventKeys로 받고, src/pages/admin/RecordsDateSelect.tsx:68(완료 n/N)과 src/pages/admin/RecordsParticipants.tsx:122(참가자 뱃지) 모두 session.eventKeys를 그대로 넘긴다. src/lib/entry-status.test.ts:46-90이 "회차별 분모 판정"·"종목 추가 후 과거 회차 상태 불변" 시나리오를 단위 테스트로 이미 못박아 뒀다(커밋 00bd333, #138). 이 이슈에서 새로 배선할 게 없고, 회귀 테스트만 한 겹 더 얹는다.

면제 토글 상수 — src/lib/exemptable-events.ts:5의 EXEMPTABLE_EVENT_KEYS는 현재 Set(['45도패스캐치']) 하나뿐이다. docs/prd-event-lifecycle.html:352 열린 항목이 "패스 3종(체스트·바운드·원핸드)에 노출"을 기본값으로 제안했고, 이슈 본문도 이 값을 그대로 채택했다(운영상 이견 없으면 확정). isExemptable을 소비하는 src/lib/player-input-field.ts:25,45-47는 이미 "면제 불가 종목에 exempt가 이미 저장된 경우"(시트 직접 편집이든, 상수 변경으로 새로 면제 불가가 된 종목이든 동일 코드 경로)를 initialFieldNotice 안내로 처리해 두고 있어 — 45도패스캐치가 면제 불가로 바뀌어도 과거 면제 기록이 있는 회차를 열면 값 입력부 대신 안내 문구가 뜨는 것으로 이미 안전하다. 이 부분은 코드 변경이 필요 없고, 상수 값 교체만 하면 된다.

3설계

  • 채택 — RecordsPlayerInput의 최상위 함수(data·session이 함께 스코프에 있는 지점)에서 eventsByKey Map을 만들고 session.eventKeys.map(...).filter(...)로 걸러진 배열을 PlayerInputContent에 events prop으로 넘긴다. PlayerInputContent 내부 로직(필드 초기화·저장 payload 조립)은 이미 events prop을 순회하는 구조라 변경이 필요 없다 — 입력 자체가 이미 회차 종목만 담고 있으면 나머지는 그대로 올바르다.
  • 기각 — PlayerInputContent 내부에서 필터링: session은 이미 prop으로 전달되고 있어 내부에서도 가능하지만, profile-view.ts·compute-rankings.ts와 동일하게 "소비 직전에 한 번 걸러서 넘긴다" 위치를 맞추는 쪽이 리포 전역의 관용구와 더 잘 맞고, PlayerInputContent의 events prop 타입 계약("이 화면이 그릴 종목")이 더 명확해진다.
  • 순서 기준은 events[]가 아니라 eventKeys: shared/domain.ts:72 주석이 eventKeys를 "헤더 순서"의 정본으로 못박고 있어, Map 조회 순서를 eventKeys.map(...)으로 둔다(목표 탭 행 순서인 events[] 자체 순서를 쓰지 않음).
  • exemptable-events 상수: 45도패스캐치 단일 키를 패스 - 체스트·패스 - 바운드·패스 - 원핸드 3키로 교체(추가가 아니라 교체 — 45도패스캐치는 종료 종목이라 신규 입력 자체가 없다). 문자열은 docs/prd-event-lifecycle.html:163-165의 표기("패스 - 체스트" 등, 하이픈 양옆 공백)를 그대로 따른다.

5리스크

리스크영향완화책
필터링 위치를 PlayerInputContent 내부로 착각하고 events prop 타입/호출부를 이중으로 바꿀 여지불필요한 diff 증가필터링은 RecordsPlayerInput(상위) 한 곳에서만, PlayerInputContent는 prop 계약만 그대로 소비
테스트 픽스처 문자열(45도패스캐치 → 패스 - 체스트) 치환 누락 시 일부 테스트만 깨짐CI 빨간불로 바로 드러남(은닉 위험 낮음)grep으로 45도패스캐치 잔여 참조를 변경 대상 파일에서 재확인 후 커밋
실제 시트 마이그레이션(§10)은 이 이슈 범위 밖 — 코드는 신규 7종목 스키마를 받아들일 준비만 함배포 시점에 시트가 아직 구 스키마면 기존처럼 500(현행과 동일, 이 PR로 악화되지 않음)마이그레이션은 별도 절차(PRD §10)로 운영자가 수행 — 이 PR은 코드만 대비
