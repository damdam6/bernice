어드민 화면에 데이터 새로 고침 버튼 추가 — 캐시 무시하고 시트 최신 데이터 강제 반영

1요약

시트 관리 홈에 "데이터 새로 고침" 버튼을 추가한다. 누르면 ① 기존 POST /api/refresh(#43)로 엣지 캐시를 퍼지하고 ② fetch(…, { cache: 'reload' })로 브라우저 HTTP 캐시를 우회해 최신 데이터를 받아 ③ setQueryData로 TanStack Query 캐시에 즉시 반영한다. reload 응답이 브라우저 캐시 엔트리를 교체하고 엣지 캐시도 재적재하므로, 버튼 한 번으로 관리자 본인과 팀원 모두 최신 데이터를 보게 된다. 서버 캐시 정책(functions/api/records.ts·records-cache.ts)은 건드리지 않는다.

2현황 분석

  • 2중 캐시 구조: GET /api/records는 엣지 Cache API에 고정 합성 키(functions/lib/records-cache.ts:7)로 6시간 저장하고(functions/api/records.ts:29), 응답 헤더 Cache-Control: public, max-age=21600(functions/api/records.ts:26)로 브라우저 HTTP 캐시에도 6시간 저장된다.
  • 퍼지 엔드포인트는 있으나 미연결: POST /api/refresh(functions/api/refresh.ts:7)가 엣지 캐시를 cache.delete하지만, 프론트 소스 전체에서 호출부가 0곳 — 현재 curl 전용이다. 인증은 functions/api/_middleware.ts:33의 401 게이트만 거친다(admin 전용 경로 아님).
  • 프론트 refetch는 브라우저 캐시에 막힘: fetchRecords(src/hooks/useRecords.ts:10)가 옵션 없는 일반 fetch('/api/records')라, invalidateQueries로 refetch해도 브라우저가 캐시된 옛 응답을 그대로 돌려줄 수 있다. 엣지만 퍼지해서는 부족한 이유다.
  • 어드민 홈: SheetManagementHome(src/pages/admin/SheetManagementHome.tsx:27)은 버튼 3개(기록 입력·참가자 추가·기록지 만들기) + 로그아웃 + 안내 카드 구성으로 데이터 갱신 수단이 없다. /admin 라우트는 AdminGate 뒤에 있다(src/App.tsx:30).
  • 기존 관용구: API 래퍼는 항상 { ok: true, … } | { ok: false, message }로 resolve(src/lib/add-players-api.ts:24), 성공 피드백은 Toast(src/hooks/useToast.ts·src/components/common/Toast.tsx), 실패는 role="alert" 인라인 문구(src/pages/admin/CreateSheet.tsx:66), 진행 중은 disabled + "…하는 중" 라벨.

3설계

흐름 (버튼 클릭 → 3단계, 순서 고정):

  1. POST /api/refresh — 엣지 캐시 퍼지. 실패하면 여기서 중단하고 에러 표시(옛 데이터를 다시 심는 낭비 방지).
  2. fetchRecords(undefined, 'reload') — cache: 'reload'는 브라우저 캐시를 건너뛰고 네트워크로 가며, 엣지도 방금 비워졌으므로 시트를 재조회한 최신 응답이 온다. 이 응답이 브라우저 캐시 엔트리를 교체하고, records.ts의 cache.put이 엣지 캐시도 재적재한다 — 팀원들도 즉시 최신을 본다.
  3. queryClient.setQueryData(RECORDS_QUERY_KEY, fresh) — 화면 즉시 갱신.

순서가 핵심: 퍼지 전에 refetch하면 엣지의 옛 응답을 받아 브라우저 캐시에 다시 심는다. 반드시 퍼지 완료 후 refetch하며, 테스트로 호출 순서를 고정한다.

기각한 대안:

  • 캐시 버스터(?t=…): 버스터 URL은 /api/records 원래 캐시 엔트리를 그대로 남겨, 이후 일반 refetch가 다시 옛 데이터에 히트한다. cache: 'reload'는 엔트리 자체를 새 응답으로 교체하고 URL 계약도 하나로 유지한다.
  • invalidateQueries로 갱신: refetch가 일반 fetch라 브라우저 캐시 의존이 남고 왕복도 이중이다. reload로 이미 받은 바디를 setQueryData로 직접 반영하는 쪽이 단순하고 원자적이다.
  • Cache-Control 축소·저장 플로우 개편: 완료 조건 "평상시 캐시 동작 불변" 위반 — 범위 밖.
  • 새 admin 전용 엔드포인트: 기존 #43 재사용으로 충분. 버튼 자체가 AdminGate 뒤라 노출면 증가 없음.

UI: 시트 관리 홈 버튼 스택 4번째(보조 스타일, "참가자 추가"와 동일)로 "데이터 새로 고침" 추가. 진행 중 disabled + "새로 고침 중…", 성공 시 Toast "최신 데이터를 불러왔어요", 실패 시 role="alert" 인라인 문구.

4작업 단계

  1. refresh API 래퍼 신설 — refreshRecordsCache(): Promise<{ ok: true } | { ok: false; message: string }>. POST /api/refresh 호출, 네트워크 오류·비2xx도 ok:false로 resolve(add-players-api 관용구). 단위 테스트 동반. ✓ 완료 · 테스트 5건 src/lib/refresh-api.ts (신규), src/lib/refresh-api.test.ts (신규)
  2. fetchRecords에 캐시 모드 매개변수 추가 — fetchRecords(signal?, cache?: RequestCache) → fetch('/api/records', { signal, cache }). 기존 호출부(useQuery queryFn)는 무변경·기본 동작 동일. reload 전달이 fetch에 그대로 실리는지 테스트 추가(완료 조건 ③ 직결). ✓ 완료 · 테스트 2건 추가 src/hooks/useRecords.ts, src/hooks/useRecords.test.tsx
  3. 새 훅 useRefreshRecords — { refreshing, refresh } 반환. refresh()가 퍼지 → reload refetch → setQueryData를 오케스트레이션하고 { ok: true } | { ok: false; message }로 resolve(refetch의 ApiError는 한국어 실패 문구로 변환). renderHook 테스트 동반. ✓ 완료 · 테스트 4건 src/hooks/useRefreshRecords.ts (신규), src/hooks/useRefreshRecords.test.tsx (신규)
  4. 시트 관리 홈 배선 — "데이터 새로 고침" 버튼(보조 스타일·4번째) + useToast/Toast 성공 피드백 + 인라인 에러 + 진행 중 disabled/"새로 고침 중…". 컴포넌트 테스트에 노출·호출 순서·성공/실패/로딩 케이스 추가. ✓ 완료 · 테스트 3건 추가 src/pages/admin/SheetManagementHome.tsx, src/pages/admin/SheetManagementHome.test.tsx
  5. 전체 회귀 — npm run typecheck + npm test(vitest run) 그린 확인. 서버 쪽 파일 무변경 확인(diff에 functions/ 없음). ✓ 완료 · typecheck 통과 · 86 파일 779 테스트 그린 (변경 없음 — 검증만)

5리스크

리스크영향완화책
cache: 'reload' 미지원 구형 브라우저버튼이 브라우저 캐시를 못 뚫음표준 fetch 옵션으로 모던 브라우저 전부 지원. 미지원이어도 최악이 "오늘과 동일"이라 회귀 없음
퍼지 성공 후 refetch 실패(네트워크·502)엣지 캐시만 비워진 채 에러 표시다음 /api/records 조회가 시트 재조회로 자연 복구. 에러 문구로 재시도 유도 — 데이터 유실 없음
setQueryData 직후 동시 background refetch가 옛 데이터로 덮어씀화면이 잠시 옛 데이터로 회귀/admin에는 useRecords 구독자가 없고 staleTime 5분 — 실질 발생 경로 없음. 발생해도 브라우저 캐시가 이미 교체돼 다음 refetch는 최신
/api/refresh가 admin 전용이 아님(team 세션도 호출 가능)—#43의 기존 계약 그대로이며 이번 변경으로 서버 노출면 증가 없음(버튼만 AdminGate 뒤에 추가)
