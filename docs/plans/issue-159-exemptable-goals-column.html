면제 가능 종목을 시트에서 관리할 수 없음 — 프론트 상수 하드코딩을 목표 탭 '면제 가능' 열로 이전

1요약

입력 화면 면제 토글의 노출 기준이 프론트 상수 src/lib/exemptable-events.ts(패스 3종 하드코딩)에 있어, 면제 가능 종목을 바꾸려면 배포가 필요하다. 목표 탭에 여섯 번째 열 면제 가능(F열)을 신설해 parse-goals가 읽고 EventDefinition.exemptable로 노출하며, 토글은 이 플래그를 따르고 상수 파일은 제거한다. 면제 의미론(서버·파서가 모든 종목의 "면제" 리터럴 수용)은 불변 — 옮기는 것은 UI 노출 기준의 원천뿐이다.

2현황 분석

  • 노출 결정: src/lib/exemptable-events.ts의 isExemptable()이 하드코딩 Set(패스 - 체스트/바운드/원핸드)을 조회. 소비처는 src/lib/player-input-field.ts:25,45(폼 초기화·안내문)와 src/pages/admin/RecordsPlayerInput.tsx:139(토글 렌더) 두 곳.
  • 목표 탭 파싱: functions/lib/parse-goals.ts:19의 EXPECTED_HEADER가 5열(종목|목표|만점|방향|종료 회차)을 검증하고 parseGoalRow()는 row[0]~row[4]만 읽는다. 만점·종료 회차는 "빈칸 또는 - = null" 관례(NULL_LITERALS, parse-goals.ts:21)를 공유.
  • 배포 순서의 핵심 근거 — 현행 배포 코드는 F열을 이미 무시한다: ① 조회 range가 무제한 탭 전체(functions/lib/sheetsApi.ts:148, '목표') ② 헤더 검증이 앞 5칸 prefix만 비교(parse-goals.ts:57, EXPECTED_HEADER.every) ③ 행 파싱이 row[0..4]만 접근. 따라서 실시트에 F열을 먼저 추가해도 배포 중인 코드는 깨지지 않는다.
  • 계약 전파 경로: shared/domain.ts:38 EventDefinition → 서버 조립(build-records-response.ts:64·api/admin/records.ts:72·api/admin/create-sheet.ts:71) → JSON 응답 → 프론트 런타임 검증 src/lib/parse-records-response.ts:56(parseEventDefinition).
  • 서버 캐시: functions/lib/records-cache.ts:7의 캐시 키가 records/v1 — 주석대로 RecordsResponse 모양이 바뀌면 버전을 올려 구캐시를 무효화해야 한다(안 올리면 배포 직후 프론트 검증이 구캐시 응답을 거부).
  • 시딩·문서: scripts/seed-sheet.mjs:41 목표 탭 5열 시드 · docs/sheet-integration.html:128 목표 탭 5열 스키마 · docs/sheet-rules.html(운영 입력 대상 열·표기 규칙 표·§08 다이어그램) · docs/records-schema.html:213 EventDefinition 계약과 예시 JSON.

3설계

  • 시트 스키마: 목표 탭 6열 — 헤더 종목 | 목표 | 만점 | 방향 | 종료 회차 | 면제 가능. F열 값 규칙: 가능 = 면제 가능, 빈칸 또는 - = 불가(만점·종료 회차의 null 관례와 일관), 그 외 값은 fail-loud(행·종목명 포함 에러).
  • 과도기 5/6열 수용: 헤더 F1이 없으면(5열) 전 종목 exemptable: false로 파싱하되, F1 헤더 없이 F열 값만 있으면 fail-loud(헤더 누락 실수 안내). F1이 있으면 정확히 면제 가능이어야 하고 값 규칙대로 파싱. G열 이후는 지금처럼 무시(이번 마이그레이션을 안전하게 만든 관례를 미래 열 추가를 위해 보존).
  • 계약: EventDefinition.exemptable: boolean 필수 필드로 추가(옵셔널로 두면 소비자마다 undefined 분기가 생겨 repo의 fail-loud 계약 스타일과 어긋남). 프론트 런타임 검증도 boolean 필수로 거부.
  • 캐시: RECORDS_CACHE_KEY를 records/v1 → v2로 범프(구캐시 자연 무효화 — /api/refresh는 같은 상수를 import하므로 자동 동행).
  • 배포 순서(확정): ① 실시트에 F1 헤더 + 패스 3종 가능 기입(현행 코드가 F열을 무시하므로 안전) → ② 머지·자동 배포(신코드가 F열 즉시 반영). 역순이 되어도 5열 수용 덕에 무중단이나, 시트 편집 전까지 패스 3종의 토글이 일시 미노출(면제는 시트 직접 편집 escape hatch로 여전히 가능)됨을 절차에 명시.
  • 기각한 대안: 6열 엄격 전용(5열 거부) — 시트 편집이 머지·자동배포보다 늦으면 records API가 500으로 전면 다운, 자율 머지 파이프라인과 양립 불가. 하드코딩 fallback 유지 — 원천 이원화로 이슈의 목적(시트 SoT) 자체를 훼손.
