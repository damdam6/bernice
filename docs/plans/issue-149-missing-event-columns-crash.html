#149버그 수정

신규 종목 추가 후 회차 탭에 컬럼이 없으면 앱 전체가 "문제가 발생했어요" 에러로 죽음

damdam6/bernice 브랜치 fix/149-missing-event-columns-crash ← main 라벨 bug 2026-07-27

1요약

관측된 크래시의 코드 원인(구 파서의 "목표 탭 종목 전체 = 회차 탭 헤더" 완전일치 강제)은 P7 종목 생애주기 시리즈(#133 V3 완화 외 #132~#148)로 이미 main에서 해소·테스트 완료됐고, 실시트도 PRD §10 정합화(목표 탭 5열 + 45도패스캐치 복원·종료 마킹)가 이미 실행된 상태임을 읽기 전용 Sheets API 진단으로 실측 확인했다. 남은 결함은 단 하나 — 프로덕션 배포가 최신 main을 반영하지 못한 스테일 상태다(배포 번들 index-KYUvzGPv.js ≠ 최신 main 로컬 빌드 index-BKMpyhsl.js 실측). 따라서 이 이슈는 ① 이슈가 기술한 원상태("신규 종목이 어느 회차 탭에도 없음")를 조립 단계 E2E 회귀로 고정하는 코드 작업과 ② CF Pages 배포 정상화·검증(PRD §10 절차 4)으로 완료된다.

2현황 분석

  • 에러 메시지의 출처 — 이슈의 "회차 탭 헤더에 다음 종목 컬럼이 없습니다: …"는 구 코드 functions/lib/parse-session.ts:161(dd96916 이전)의 V3 완전일치 검증 메시지와 정확히 일치한다. 현행 main에는 이 검사가 존재하지 않는다 — V3 완화로 제거됐고 그 사실이 functions/lib/parse-session.ts:185-187 주석에 명시돼 있다.
  • 타임라인 — V3 완화(#133, dd96916)는 07-27 06:53 KST 머지, P7 마지막 커밋(#148, 124ce77)은 20:26 KST, 이슈 생성은 20:54 KST. 즉 관측 시점의 프로덕션은 06:53 이전 코드를 실행 중이었다.
  • 실측 1 — 배포 스테일 확정: 프로덕션(bernice-a5v.pages.dev)의 번들은 assets/index-KYUvzGPv.js, 최신 main을 로컬 빌드하면 index-BKMpyhsl.js. Vite 해시는 내용 기반이라 불일치 = 스테일. /api/health는 200(서비스 자체는 동작), /api/records는 익명 401(미들웨어 정상).
  • 실측 2 — 실시트는 이미 정합화 완료 (Sheets API 읽기 전용 진단): 목표 탭 헤더 5열(종목|목표|만점|방향|종료 회차), 9행에 45도패스캐치|5|7|높을수록|2025-05-16 복원, 2025-05-16 탭 헤더 = 45도패스캐치 포함 4종목, 2026-07-23 탭 헤더 = 신규 7종목. PRD §10 절차 1~3이 전부 실행된 상태로, E2E 스모크(functions/api/records.e2e.test.ts, #147)의 픽스처와 동일하다.
  • 구 코드 × 현행 시트 = 이슈 재현 — 구 코드는 목표 탭에서 8종목을 읽고 2025-05-16 헤더(4종목)에서 신규 4종목(패스 - 체스트·바운드·원핸드, 볼 캐치)을 찾지 못해 정확히 이슈의 메시지로 throw한다. 신규 코드는 같은 입력을 200으로 처리한다(#147 E2E가 동일 픽스처로 전 구간 증명).
  • 에러가 캐시로 고착될 가능성 없음 — functions/api/records.ts:25-30은 200 응답만 cache.put한다. 500은 캐시되지 않으므로 배포만 정상화되면 즉시 복구된다.
  • 이슈 완료 조건 3(파서 테스트)은 기충족 — functions/lib/parse-session.test.ts:193("목표 탭에 있어도 회차 헤더에 없는 종목은 에러가 아니라 '그 회차 미측정'") 및 302~358행 "회차별 종목 서브셋(V3 완화)" 블록이 #133에서 추가됐다.

3원인 분석

  • 근본 원인(코드, 기해소) — 구 mapHeaderToEvents의 V3 완전일치 강제: 종목을 하나만 추가해도 그 컬럼이 없는 모든 과거 회차 탭이 에러가 되어 /api/records 전체가 500 → 프론트 전면 에러 화면. PRD docs/prd-event-lifecycle.html §01 문제 1의 실제 발생 사례이며, §10 진단표는 이 전면 에러 상태와 "신규 코드 배포로만 복구된다"까지 이미 문서화했다.
  • 현재 잔존 원인(운영) — CF Pages GitHub 연동 자동 빌드가 최신 main을 배포하지 못하고 있다(실패·중단·미트리거 여부는 대시보드에서 확인 필요). 수동 wrangler pages deploy는 스테일 dist/를 덮는 split-brain 사고 이력이 있어 금지 — 복구는 GUI 재빌드가 정석.
  • ⚠ 작업 중 정정 (구현 세션 실측) — 위 항목의 "자동 빌드 미동작" 가설은 틀렸다. wrangler pages deployment list(읽기 전용) 결과 CF 연동은 main 푸시마다 정상 빌드·배포 중이며, 최신 main(124ce77)의 정상 배포 e6ff5fd6(번들 index-BKMpyhsl.js = 로컬 최신 빌드와 일치)가 실존한다. 실제 원인: 그 약 13분 뒤 옛 main 커밋 0a353de(#109 PRD 문서 시점, P7 코드 이전) 기준으로 빌드된 새 Production 배포 97d7522d(번들 index-KYUvzGPv.js)가 올라와 프로덕션 별칭을 덮었다 — 대시보드에서 옛 배포를 Retry했거나 옛 체크아웃에서 수동 배포된 것으로 추정. 복구는 최신 main의 새 배포 1회(이 PR 머지가 자동 트리거) 또는 GUI에서 e6ff5fd6 재지정. 옛 배포의 Retry는 금지(같은 사고 재발).
  • 기각한 가설 — ⓐ "실시트 미마이그레이션이라 새 코드도 V5(functions/lib/parse-goals.ts:55-61 5열 엄격 일치)로 죽는다" → 실측으로 기각(이미 5열). ⓑ "새 코드에 잔존 크래시 경로가 있다" → #147 E2E가 실시트와 동일한 목표·헤더 픽스처로 200 증명, 데이터 행은 사고 전부터 파싱되던 그대로. ⓒ "에러 응답이 캐시에 남는다" → 200만 캐시됨.

4작업 단계

  1. ✅ 운영CF Pages 대시보드에서 최근 main 커밋들의 빌드 이력 확인 — 실패면 로그로 원인 파악, 미트리거·중단이면 최신 main 재빌드를 트리거한다(사용자 GUI 조율). 수동 배포는 최후수단으로만, 반드시 npm run build && npx wrangler pages deploy 세트로. Cloudflare Pages GUI (bernice-a5v) — 코드 변경 아님, PR과 독립적으로 즉시 진행 가능 결과(진단 완료·원인 정정): 읽기 전용 wrangler pages deployment list로 규명 — CF 연동은 정상, 옛 커밋 0a353de 기준 배포 97d7522d가 최신 정상 배포 e6ff5fd6(124ce77)를 덮은 것이 원인(원인 분석 ⚠ 정정 항목 참고). 남은 액션은 "PR 머지 → 자동 배포" 하나로 축소됨
  2. ✅ 코드이슈 원상태 회귀 E2E 추가 — "신규 종목이 목표 탭에만 있고 어떤 회차 탭 헤더에도 없는" 번들(목표 8종목 + 회차는 2025-05-16 하나뿐): 200 응답, events[] 8종목 유지, sessions[0].eventKeys 4종목으로 좁힘, 신규 4종목 trends points: []·personalBests 부재, home.achievementRates는 최신 회차 측정 종목만. 종목 추가 직후·새 기록지 생성 전이라는 정상 운영 구간(PRD §11 "과거 회차 탭은 손대지 않는다")의 조립 단계 계약을 고정한다. functions/api/records.e2e.test.ts 결과: describe "신규 종목이 목표 탭에만 있고 어떤 회차 탭에도 없음 (#149)" 4케이스 추가 — 계획한 어서션 전부 포함
  3. ✅ 코드전체 테스트 그린 확인 — 신규 케이스 포함 vitest 전체 통과, 기존 스위트 회귀 없음. npm test 결과: 84파일 765테스트 전부 통과 + npm run build(타입체크 포함) 그린
  4. ⏳ 검증배포 후 프로덕션 검증 — ⓐ 배포 번들 해시가 로컬 main 빌드와 일치, ⓑ 앱 정상 렌더(에러 화면 없음), ⓒ PRD §10 기대 화면: 랭킹 2025-05-16은 45도패스캐치 포함 4종목 칩·최신 회차는 신규 7종목 칩·홈 게이지 7종목·프로필 1차 참가자에게 45도패스캐치 종료 뱃지 카드. https://bernice-a5v.pages.dev — 프리뷰 환경은 시크릿 부재로 검증 불가, 프로덕션에서만 상태: PR 머지 → 자동 배포 후 수행 (머지가 곧 복구 트리거)
  5. ⏳ 운영(조건부) 검증 과정에서 시트를 추가 편집한 경우에만 /api/refresh(로그인 필요)로 6시간 캐시를 무효화한다. functions/lib/records-cache.ts — TTL 6h, 200만 캐시
  6. ✅ 코드PR 생성 — 회귀 E2E + 최종 플랜 문서 커밋, Closes #149. 코드 원인은 이미 main에 있으므로 이 PR은 "재발 방지 계약 고정"이 본체다. docs/plans/issue-149-missing-event-columns-crash.html

5리스크

리스크영향완화책
CF Pages 빌드 실패 원인이 환경(노드 버전·환경변수 등)이면 재트리거로 안 풀림배포 지연 — 앱 다운 지속빌드 로그 우선 확인(로컬 빌드는 성공하므로 코드보다 설정 의심). 최후수단: npm run build && npx wrangler pages deploy 세트(단독 deploy 절대 금지 — split-brain 사고 이력)
번들 해시 비교의 위양성(빌드 환경 차이)스테일 오판배포 완료 후 같은 커밋 기준으로 재대조하고, CF GUI에서 배포 커밋 SHA를 직접 확인해 이중 검증
실시트 데이터 행에 별개의 fail-loud 요인(명단 불일치 등)이 숨어 있을 가능성배포 후에도 다른 메시지로 500가능성 낮음(데이터 행은 사고 전부터 파싱되던 그대로). 필요시 배포 전 읽기 전용 실데이터 스모크(시트 fetch → 최신 buildRecordsResponse 로컬 실행)로 선검증
프리뷰 배포로 검증을 시도프리뷰는 시크릿 부재로 /api/records 1101 — 코드 문제로 오판검증은 main 머지 후 프로덕션에서만 수행 (기지 사항)
운영자가 검증 중 시트를 편집하면 6시간 캐시가 옛 200을 유지수정이 화면에 반영 안 됨편집 후 /api/refresh 호출을 검증 절차에 포함(작업 단계 5)

6테스트 계획

  • 회귀(신규) — 작업 단계 2의 E2E 케이스: 신규 종목이 어느 회차 탭에도 없는 번들이 200으로 조립되고 eventKeys·trends·home이 PRD대로 좁혀지는지. 이슈 재현 상태가 다시는 에러가 되지 않음을 조립 단계에서 고정.
  • 기존 동작 — vitest 전체 스위트 그린: parse-session V3/V4 단위(parse-session.test.ts:193, 302-430), 혼재 번들 E2E 6케이스 + V4·V6 위반 2케이스(records.e2e.test.ts), 프론트 파생·화면 테스트 전부.
  • 프로덕션 수동 검증 — 작업 단계 4의 체크리스트(§10 절차 4 + 기대 화면). 완료 판정의 최종 근거.
