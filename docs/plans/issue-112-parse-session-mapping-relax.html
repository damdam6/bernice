P7 — parse-session 매핑 완화: 회차별 종목 서브셋(V3) + 종료 경계 검증(V4)

damdam6/bernice 브랜치 feat/112-parse-session-mapping-relax ← main 라벨 enhancement 2026-07-27

1요약

mapHeaderToEvents가 강제하던 "목표 탭 종목 전체 = 회차 탭 헤더" 완전일치를 깨고, 회차 탭 헤더를 그 회차에 무엇을 측정했는지의 정본으로 승격한다. 목표에 있는데 헤더에 없는 종목은 에러가 아니라 "그 회차 미측정"이 되고(V3 완화), 대신 종료된 종목이 종료 회차 이후에 다시 등장하면 새 에러로 잡는다(V4 신설). V1(목표에 없는 헤더)·V2(중복 헤더·빈 헤더 셀)는 그대로 유지해 fail-loud 철학은 흔들지 않는다. Session.eventKeys·scores 서브셋·participated 분모는 이미 eventColumns를 따라 파생되므로 코드 변경 없이 완화의 결과로 따라오고, 이 계약을 테스트로 못박는 것이 이 이슈의 나머지 절반이다.

2현황 분석

읽기 경로 — functions/lib/build-records-response.ts:57이 회차 탭마다 parseSession(round.name, round.values, playersByName, events)을 호출하고, parseSession은 functions/lib/parse-session.ts:58에서 mapHeaderToEvents(rows[0], events)로 헤더를 종목 열에 매핑한다. 반환된 eventColumns가 그 뒤의 모든 파생을 결정한다:

  • parse-session.ts:98-100 — scores는 eventColumns만 순회해 채운다. 즉 이미 "헤더 종목만" 채우는 구조다.
  • parse-session.ts:102 — participated는 Object.values(scores).some(...)이라 분모가 자동으로 그 회차 측정 종목이 된다.
  • parse-session.ts:107 — eventKeys: eventColumns.map(({ event }) => event.key). #110에서 이미 배선됐고 build-records-response.ts:36이 탈퇴 필터링 후에도 그대로 실어 나른다.

따라서 이슈 범위 중 "eventKeys 포함 · scores는 헤더 종목만" 두 항목은 구조상 이미 성립해 있고, 실제로 막고 있는 것은 parse-session.ts:159-162의 마지막 검사 한 덩어리뿐이다:

  • const missing = events.filter(...) → 목표 탭 종목 중 헤더에 없는 것이 하나라도 있으면 회차 탭 헤더에 다음 종목 컬럼이 없습니다: …로 throw. 이것이 PRD §01 문제 1(종목 추가 순간 과거 회차 전부가 500)의 코드상 원인이다.

쓰기 경로 — functions/api/admin/records.ts:99이 같은 mapHeaderToEvents(round.values[0], events)를 integrity()로 감싸 호출한다(functions/lib/record-write.ts:8,11이 재-export). 그래서 이 함수 하나만 고치면 완화·검증이 읽기/쓰기에 동일하게 적용된다 — PRD §09가 "POST /api/admin/records는 사실상 변경 없음"이라고 적은 근거가 이 재사용이다.

V4에 필요한 입력 — 종료 경계 판정에는 "그 회차 날짜"가 필요한데 현재 mapHeaderToEvents(header, events)는 날짜를 받지 않는다. 두 호출부 모두 날짜를 갖고 있다: parseSession은 tabName(parse-session.ts:49), 엔드포인트는 round.name/sessionDate(records.ts:87). 회차 탭 이름은 functions/lib/sheetTabs.ts의 parseRoundDate가 캘린더 유효성까지 왕복 검증하므로 항상 YYYY-MM-DD임이 보장된다.

endSessionDate의 현재 값 — functions/lib/parse-goals.ts:70이 아직 endSessionDate: null을 하드코딩한다(5열 파싱은 #111). 따라서 V4는 이 이슈 시점에서 프로덕션 데이터로는 절대 발화하지 않고, 이슈 본문대로 픽스처로 주입해 테스트한다. 이 독립성이 #111과 병렬 진행을 가능하게 한다.

기존 테스트 지형 — functions/lib/parse-session.test.ts:193-197에 완전일치를 보장하는 테스트(종목 컬럼이 누락되면 Error를 던진다)가 있어 이번 변경으로 의미가 뒤집힌다. parse-session.test.ts:296-305의 빈 헤더 셀 테스트는 유지되지만 주석이 "missing-컬럼 체크로는 안 걸리는"이라는 사라질 검사를 근거로 든다. functions/lib/record-write.test.ts:144,155는 mapHeaderToEvents를 직접 호출해 시그니처 변경의 영향을 받는다.

3설계

결정 1 — V4는 mapHeaderToEvents 안에 둔다. 대안은 parseSession에서 매핑 후 별도 검사하는 것이지만, 그러면 쓰기 경로(records.ts:99)가 V4를 상속하지 못해 "완화·검증이 읽기/쓰기 동일 적용"(이슈 범위 · PRD §07)이 깨진다. 규칙 원천을 하나로 두는 PRD §08과도 어긋난다.

결정 2 — sessionDate는 필수 3번째 인자. 선택 인자로 두면 호출부가 조용히 V4를 건너뛸 수 있고, 그 누락은 타입 검사로 잡히지 않는다. 두 호출부 모두 이미 날짜를 손에 쥐고 있어 필수화 비용이 0이다. 시그니처: mapHeaderToEvents(header: string[], events: EventDefinition[], sessionDate: string): EventColumn[].

결정 3 — 날짜 비교는 YYYY-MM-DD 문자열 사전식 비교. 두 값 모두 고정 폭 YYYY-MM-DD이므로 사전식 순서 = 시간 순서다. sessionDate > event.endSessionDate일 때만 에러 — 같은 날(경계, PRD §05 "종료 회차로 지정된 회차 자체에 컬럼이 있는 것은 정상")과 이전 날짜는 통과한다. Date 객체 파싱은 타임존·유효성 처리를 새로 떠안을 뿐 이득이 없어 배제한다. 형식 보증의 출처는 회차 쪽이 sheetTabs.parseRoundDate, 종목 쪽이 #111의 V5이며 이 함수는 그 계약을 신뢰한다(주석으로 명시).

결정 4 — 검사 순서는 V1·V2 → V4. V4는 매핑에 성공한 열에 대해서만 의미가 있으므로 기존 루프 안에서 event를 찾은 직후 검사한다. 헤더가 깨진 경우(V1·V2)에는 그 사유가 먼저 나오는 편이 운영자에게 정확하다.

결정 5 — 범위 밖으로 명시적으로 남기는 것. 이 이슈는 mapHeaderToEvents 한 함수와 그 계약 테스트까지다.

  • V6(종료 회차 ↔ 실존 회차 탭 대조)는 회차 목록을 아는 조립 단계 — #120.
  • 엔드포인트 4xx 계약(요청 scores에 그 회차 비측정 종목 key가 올 때) — #122. 여기서는 record-write.ts가 재-export한 함수가 같은 완화·같은 V4를 준다는 것까지만 테스트로 못박는다.
  • 서브셋 회차의 하류 계산(computeSessionRankings·player-summary 가드) — #113·#114. 이 이슈에서는 parseSession 반환값까지만 검증하고 조립 경로에 서브셋 픽스처를 밀어 넣지 않는다.
  • 목표 탭 5열 파싱(V5) — #111. endSessionDate는 픽스처로만 주입한다.

4작업 단계

  1. V3 완화 — mapHeaderToEvents 말미의 missing 계산·throw 블록을 제거한다. 상단 주석에 "헤더가 그 회차 측정 종목의 정본이며 목표에만 있는 종목은 미측정"이라는 규칙과 PRD §05 V3 근거를 남긴다. functions/lib/parse-session.ts
  2. 시그니처에 sessionDate 추가 — mapHeaderToEvents(header, events, sessionDate)로 필수 인자를 넣고, parseSession은 tabName을, 엔드포인트는 round.name을 넘기도록 호출부를 갱신한다. functions/lib/parse-session.ts, functions/api/admin/records.ts
  3. V4 신설 — 헤더 열 매칭 루프 안에서 event.endSessionDate !== null && sessionDate > event.endSessionDate이면 종목명·회차 날짜·종료 회차를 담은 메시지로 throw한다. 경계(같은 날짜)는 통과. 사전식 비교의 근거를 주석에 남긴다. functions/lib/parse-session.ts
  4. 기존 V3 테스트 반전 — 종목 컬럼이 누락되면 Error를 던진다를 "컬럼이 없는 종목은 미측정으로 빠진다"로 바꾼다. eventKeys에서 제외되고 scores에 key 자체가 없음을 함께 단언한다. 빈 헤더 셀 테스트의 주석에서 사라진 missing-체크 언급을 갱신한다. functions/lib/parse-session.test.ts
  5. 서브셋 계약 테스트 추가 — 4종목 목표 × 2종목 헤더 픽스처로 ① eventKeys가 헤더 순서로 2개 ② scores key 집합이 정확히 그 2개(비측정 종목 key 부재) ③ participated가 그 회차 종목만 분모로 판정(헤더 종목 전부 빈칸 → false, 하나라도 값 있으면 true)을 검증한다. functions/lib/parse-session.test.ts
  6. V4 테스트 추가 — endSessionDate를 픽스처로 주입해 ① 종료 회차 < 회차 날짜 + 컬럼 존재 → throw ② 종료 회차 == 회차 날짜 + 컬럼 존재 → 정상(경계) ③ 종료 회차 < 회차 날짜 + 컬럼 없음 → 정상(V3 완화와의 합류) ④ 종료 회차 > 회차 날짜 + 컬럼 존재 → 정상. V1·V2 유지 테스트가 그대로 통과하는지도 확인한다. functions/lib/parse-session.test.ts
  7. 쓰기 경로 동일 적용 테스트 — record-write.ts가 재-export한 mapHeaderToEvents로 ① 서브셋 헤더가 통과하고 buildWritePlan 범위가 헤더 열 기준으로만 잡히는지 ② 같은 픽스처에서 V4가 동일하게 발화하는지를 검증한다. 기존 호출부(record-write.test.ts:144,155)에 sessionDate 인자를 채운다. functions/lib/record-write.test.ts
  8. 전체 회귀 — npm test·npm run typecheck으로 681개 기존 테스트와 타입이 그대로 통과하는지 확인한다(완전일치 픽스처는 완화 후에도 동작이 같아야 한다). package.json

5리스크

리스크영향완화책
V3 완화로 하류(computeSessionRankings·player-summary)가 서브셋 회차에서 터질 수 있다 — PRD §07이 collectValidScores의 TypeError를 명시 서브셋 시트가 실제로 들어오면 조립 단계에서 런타임 오류 이 이슈는 하류에 서브셋을 흘리지 않는다 — 테스트는 parseSession 반환값까지만 검증. 하류 가드는 #113·#114 소관이고, 프로덕션에서는 parse-goals가 아직 종료 종목을 만들지 않아 서브셋 회차가 조립까지 도달하지 않는다. 통합 시나리오는 #127 E2E가 담당
V3 검사가 사라져 "회차 탭이 통째로 깨져 종목 컬럼이 하나도 없는" 사고가 조용히 통과할 수 있다 전 종목 미측정 회차로 오인 — 데이터 손실이 아니라 표시 누락 PRD §05가 D2로 의도한 트레이드오프(헤더가 정본, 측정 생략 회차 허용)라 이 이슈에서 되돌리지 않는다. 대신 V1·V2가 유지돼 "깨진 참조 수식"(빈 셀·미지 종목)은 여전히 즉시 에러다 — 실제 파손 모드는 대부분 이쪽으로 잡힌다
mapHeaderToEvents는 공개 export이고 쓰기 경로가 재-export한다 — 시그니처 변경이 호출부를 놓치면 컴파일이 깨진다 빌드 실패 호출부는 3곳(parse-session.ts:58, records.ts:99, record-write.test.ts)으로 전수 확인됨. sessionDate를 필수 인자로 두어 tsc -b가 누락을 반드시 잡게 한다
사전식 날짜 비교가 형식이 어긋난 endSessionDate에서 무의미해진다 V4 오판(놓치거나 잘못 발화) 회차 쪽은 sheetTabs.parseRoundDate가, 종목 쪽은 #111의 V5가 형식을 보증한다. 이 함수는 그 계약을 신뢰한다는 점을 주석으로 명시해 재검증 중복을 만들지 않는다

  • V1 유지: 목표에 없는 헤더(윗몸일으키기) → 여전히 Error.
  • V2 유지: 중복 헤더 → Error, 빈 헤더 셀 → Error(missing 체크 제거 후에도).
  • V4 신설(위반): endSessionDate: '2025-05-16' 종목이 2025-06-20 회차 헤더에 존재 → 종목명·두 날짜를 담은 Error.
  • V4 경계(정상): endSessionDate: '2025-05-16' 종목이 2025-05-16 회차 헤더에 존재 → 정상 파싱(마지막 측정 회차).
  • V4 + V3 합류(정상): 종료 종목이 이후 회차 헤더에 없음 → 정상, eventKeys에서 자연 소멸.
  • V4 미래 종료(정상): endSessionDate가 회차 날짜보다 뒤 → 정상(아직 현역 구간).

  • 쓰기 경로 동일 적용: record-write.ts 재-export 경유로 서브셋 헤더가 통과하고 buildWritePlan 범위가 헤더 열만 덮으며, 같은 픽스처에서 V4가 동일하게 발화한다.
