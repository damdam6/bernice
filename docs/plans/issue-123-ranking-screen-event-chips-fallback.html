P7 — 랭킹 화면: 선택 회차 측정 종목 칩 + 폴백

damdam6/bernice 브랜치 feat/123-ranking-screen-event-chips-fallback ← main 라벨 enhancement 2026-07-27

1요약

랭킹 화면의 종목 칩이 지금은 전역 events[] 전체를 렌더해, 선택한 회차에서 측정하지 않은 종목을 눌러도 "표시할 기록이 없습니다"만 뜨는 막다른 화면이 생긴다. 종목 칩을 선택 회차의 Session.eventKeys(헤더 순서)만으로 좁히고, 회차를 전환했을 때 선택 중인 종목이 새 회차에 없으면 그 회차의 첫 종목으로 자동 폴백하도록 src/pages/Rankings.tsx의 파생 순서를 바꾼다. 이미 회차별 종목 파생이 끝난 ranking-view.ts·Session.eventKeys 계약(#116) 위에 얇게 얹는 작업이라 디자인·서버 변경은 없다.

2현황 분석

src/pages/Rankings.tsx:52-70(수정 전)의 파생 순서:

  1. event = events.find(e => e.key === selectedEventKey) ?? events[0] — 선택 회차와 무관하게 전역 종목 목록에서 찾는다.
  2. sessionDate를 구하고 session은 그 아래에서 별도로 찾는다.
  3. 종목 칩도 events.map(...)로 전역 7종목(마이그레이션 후 기준) 전부를 그린다.

결과: 최신 회차(7종목)에서 종목을 고른 뒤 과거 회차(예: 4종목만 측정)로 전환해도 칩은 여전히 7개가 보이고, 방금 고른 종목이 그 회차에 없으면 rows가 빈 배열이 되어 EmptyState("표시할 기록이 없습니다")만 남는다 — 종목이 실제로 없는 게 아니라 화면이 잘못된 종목을 붙들고 있는 것이라 사용자 입장에서 오해를 준다.

이미 있는 재료:

  • shared/domain.ts:72 — Session.eventKeys: string[], "그 회차 탭 헤더의 측정 종목 key 목록(헤더 순서)". 참가자 0명 회차에도 항상 명시된다는 계약이라 entries에서 유추할 필요가 없다.
  • src/lib/ranking-view.ts의 buildRankingRows(#116에서 score undefined 가드 추가)·findTiedRanks·buildEventGuidance — 전부 "이미 선택된 종목 하나"를 받는 순수 함수라 이번 변경과 무관, 그대로 재사용.
  • src/lib/entry-status.ts:15 — 같은 eventKeys 계약을 판정 분모로 쓰는 선례(#117). 이번 작업의 "칩 목록 = eventKeys" 패턴과 결이 같다.

PRD 근거: docs/prd-event-lifecycle.html §08 "🏆 랭킹" — "종목 칩 = 선택 회차의 측정 종목만(eventKeys 순서). 회차를 전환해 선택 중인 종목이 새 회차에 없으면 첫 종목으로 폴백한다. … 7종목 칩은 기존 가로 스크롤 UI로 수용(디자인 변경 없음)."

3설계

선택한 접근 — ranking-view.ts에 deriveSessionEvents(events, session) 순수 함수 추가 + Rankings.tsx 파생 순서만 재배열.

  • deriveSessionEvents(events: EventDefinition[], session: Session): EventDefinition[] — session.eventKeys 순서대로 events에서 찾아 담고, 매치되지 않는 키(계약 위반 데이터)는 크래시 대신 건너뛴다. buildRankingRows의 "undefined 방어는 유지"(PRD §08) 기조와 동일한 방어 스타일.
  • RankingsContent에서 session을 먼저 구하고, 그 다음 sessionEvents = deriveSessionEvents(events, session), 그 다음 event = sessionEvents.find(...) ?? sessionEvents[0] 순서로 바꾼다. 폴백은 이 한 줄이 회차가 바뀔 때마다 자동으로 재평가하며 처리 — 별도의 "회차 전환 시 종목 리셋" 이펙트나 상태 동기화 코드가 필요 없다(리렌더마다 순수 파생이라 useEffect 불필요).
  • 종목 칩 렌더를 events.map → sessionEvents.map으로 교체. FilterChip·overflow-x-auto 가로 스크롤 컨테이너는 그대로 재사용(디자인 변경 없음, PRD §08 명시).

기각한 대안 — useEffect로 회차 변경 감지 후 setSelectedEventKey 직접 리셋: 상태 동기화 버그(이펙트 실행 타이밍, 초기 마운트 케이스)를 만들 뿐 아니라 기존 컴포넌트가 이미 "파생값이 상태보다 우선"하는 패턴(event = events.find(...) ?? events[0] 자체가 그 예)을 쓰고 있어 일관성이 깨진다. sessionEvents 기반 파생 하나로 렌더마다 자동 정합되므로 이펙트가 아예 불필요하다.

기각한 대안 — events 전체 대신 rankings[].events(그 회차 랭킹이 실제로 존재하는 종목)를 칩 기준으로 사용: SessionRankings.events는 "미측정 종목×회차 조합은 항목 자체가 없다"는 계약이라 eventKeys와 결과적으로 같은 집합이지만, 참가자 전원이 면제/미측정이라 EventRanking.entries가 0건인 회차·종목 조합에서도 rankings[].events 항목 자체는 존재해야 정확한데 이 경로는 그 보장이 이번 작업 범위 밖(§07 백엔드 계약)이라 직접 근거로 쓰기엔 간접적이다. Session.eventKeys가 "그 회차에 무엇을 측정했나"의 1차 출처(PRD §06 콜아웃)이므로 이걸 직접 쓴다.

4작업 단계

  1. deriveSessionEvents(events, session) 추가 — session.eventKeys 순서대로 events에서 정의를 찾아 배열로 반환, 매치 실패 키는 필터링 src/lib/ranking-view.ts
  2. deriveSessionEvents 단위 테스트 — eventKeys 순서 보존(events[] 선언 순서 무시), 부분집합(혼재 회차), 매치 실패 키 방어 src/lib/ranking-view.test.ts
  3. RankingsContent 파생 순서 재배열 — session을 먼저 구하고 sessionEvents → event(폴백 포함) 순으로, 종목 칩 렌더를 sessionEvents 기준으로 교체 src/pages/Rankings.tsx
  4. 화면 단위 회귀 테스트 — (a) 회차 전환 시 칩 목록 갱신 + 선택 종목이 새 회차에 없으면 첫 종목 폴백, (b) 혼재 픽스처(1차 4종목 칩 · 최신 7종목 칩) 렌더 src/pages/Rankings.test.tsx
  5. npm run typecheck · npm run test 전체 통과 확인 (기존 Rankings.test.tsx 회귀 없음 포함) 추가로 npm run build(CI 동일 단계)도 통과 확인

5리스크

리스크영향완화책
sessionEvents가 빈 배열이 되는 경우(회차에 측정 종목 0개)sessionEvents[0]이 undefined가 되어 event.key 접근 시 런타임 에러계약상 발생 불가(§06 콜아웃 — 참가자 0명 회차도 eventKeys는 항상 명시). 기존 코드도 events[0]을 동일하게 무가드로 썼으므로 이 작업이 새 리스크를 만들지 않음 — 별도 방어 코드 추가하지 않음
기존 Rankings.test.tsx 회귀두 회차가 같은 eventKeys를 쓰는 기존 픽스처는 동작 변화가 없어야 함기존 테스트 그대로 유지(수정 없음)하고 전체 통과 확인 — 변경은 신규 테스트로만 커버
