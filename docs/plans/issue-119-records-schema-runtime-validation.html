1요약

이슈 #110(PR #130, 계약 키스톤)에서 shared/domain.ts와 src/lib/parse-records-response.ts에 이미 EventDefinition.endSessionDate·Session.eventKeys가 반영되고 런타임 검증 로직도 추가됐다. 하지만 docs/records-schema.html(§05 타입 정의 전문·§06 예시 응답)은 그 개정을 반영하지 못한 채 남아 있고, 신규 필드를 겨냥한 명시적 런타임 검증 테스트도 없다. 이번 작업은 로직 변경 없이 문서를 domain.ts 주석·docs/prd-event-lifecycle.html §06 계약표와 정합시키고, endSessionDate·eventKeys의 성공/실패 케이스 테스트를 추가한다.

2현황 분석

이미 완료된 부분(#110/#130, 커밋 ecb4084) — 로직·타입은 정본이 이미 개정 완료 상태:

  • shared/domain.ts:38-48 — EventDefinition.endSessionDate: string | null 신설, 3줄 주석(종료 회차·events[] 전체 보관 이유·파생 규칙)
  • shared/domain.ts:59-65 — SessionEntry.scores 완전성 계약 주석이 "events[] 전체 key 존재"에서 "그 회차 Session.eventKeys 전체가 항상 존재, 그 외 key는 없음"으로 개정
  • shared/domain.ts:68-74 — Session.eventKeys: string[] 신설 + 주석
  • shared/domain.ts:93-97 — SessionRankings.events에 "그 회차 eventKeys에 해당하는 종목만" 주석 신설
  • shared/domain.ts:126-130 — PlayerSummary.trends 주석에 "(종료 종목 포함)" 삽입
  • src/lib/parse-records-response.ts:56-74 — parseEventDefinition이 이미 endSessionDate를 string | null로 검증
  • src/lib/parse-records-response.ts:117-131 — parseSession이 parseStringArray로 eventKeys를 이미 검증

미반영 부분(이 이슈의 실제 범위):

  • docs/records-schema.html:230-241 — §05 SessionEntry.scores 주석이 구 버전("events[] 전체 key가 항상 존재")이고, Session에 eventKeys 필드가 없음

  • src/lib/parse-records-response.test.ts — FULL_RESPONSE 픽스처가 두 필드값을 포함하긴 하나(10-11행, 57행), 그건 전체 응답 성공 케이스 1건에 곁다리로 낀 것일 뿐 — endSessionDate·eventKeys 각각을 겨냥한 성공/실패 케이스가 없음

3설계

문서 동기화: domain.ts 주석 문구를 그대로(의미 보존) §05 코드 블록에 옮긴다 — 별도 표현으로 의역하면 "shared/domain.ts 주석과 문구 일치"라는 완료 조건을 재차 어길 위험이 있으므로 문구를 그대로 복사한다. §06 예시 JSON에는 각 종목에 endSessionDate(예시 2종목 모두 현역이므로 null), sessions[].eventKeys(그 회차 종목 key 배열)를 추가해 계약을 시각적으로도 보여준다.

테스트: 기존 parseRecordsResponse describe 블록에 it을 추가하는 방식(신규 describe 분리보다 기존 스타일과 일관) — endSessionDate는 (a) 문자열 값 성공 (b) null 성공 (c) 숫자 등 다른 타입 거부 3케이스, eventKeys는 (a) 문자열 배열 성공(기존 FULL_RESPONSE로 이미 커버되므로 실패 케이스 위주로 추가) (b) 비배열 거부 (c) 원소에 비문자열 섞인 경우 거부 케이스를 추가한다. 로직 변경은 없음 — 파서는 이미 존재하므로 문서·테스트만 갱신하는 순수 회귀 작업.
