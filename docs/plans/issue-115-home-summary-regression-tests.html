P7 — compute-home-summary: 회차별 종목 회귀 테스트

damdam6/bernice 브랜치 feat/115-home-summary-regression-tests ← main 라벨 enhancement 2026-07-27

1요약

§06 도메인 타입 개정(#110, 이미 병합)으로 SessionRankings.events는 "그 회차 측정 종목만" 담는 계약으로 바뀌었다. computeHomeSummary는 이 SessionRankings를 필터 없이 그대로 집계하므로, 입력이 회차별로 좁혀지면 achievementRates도 자동으로 최신 회차 종목만 담게 된다 — 즉 실제 코드 변경은 없다. 이 플랜은 그 불변 규칙(최신 회차 종목만 집계, eligibleCount = 0 가드, participantCount 규칙)을 회귀 테스트 2건으로 못박는 작업만 다룬다.

2현황 분석

대상 함수는 functions/lib/compute-home-summary.ts:10-38 전체(38줄짜리 파일 하나)다:

  • participantCount — compute-home-summary.ts:19-21에서 활동 상태 + participated: true만 필터링, :35에서 반환.
  • achievementRates — compute-home-summary.ts:23-32에서 latestRankings.events.map(...)로 계산, :36에서 반환. 별도 종목 필터를 두지 않고 SessionRankings.events가 이미 들고 있는 것을 그대로 순회한다(파일 헤더 주석 :1-4가 이 설계 의도를 명시 — computeEventRanking(#28)과 같은 필터를 두 곳에 중복 구현하면 규칙이 어긋날 위험이 있어서 일부러 재필터링하지 않는다).
  • eligibleCount — compute-home-summary.ts:24 (eventRanking.entries.length), 0-가드는 :30.
  • 호출 계약: rankings는 sessions와 1:1 인덱스 대응(sessions.map(computeSessionRankings) 전제) — compute-home-summary.ts:8-9 주석. 그래서 sessions.at(-1)과 rankings.at(-1)이 항상 같은 회차를 가리킨다.

기존 테스트 functions/lib/compute-home-summary.test.ts(97줄, it 5개)는 없음/단일회차/다회차 케이스를 덮지만, 다회차 케이스(:84-96)조차 두 회차가 같은 단일 종목(골밑슛)만 측정한다 — 즉 "회차마다 측정 종목 구성 자체가 다른" 상황은 아직 아무 테스트도 없다. 이게 #115가 채우려는 공백이다.

주의할 점: 실제 운영 파이프라인에서 이 좁혀짐이 아직 실제로 일어나지 않는다 — computeSessionRankings(functions/lib/compute-rankings.ts:69-74)는 여전히 호출자가 넘긴 events 전체를 entries: []로 개수 맞춰 순회하는 구식 로직이고(#113, 아직 OPEN), 프로덕션 호출부 build-records-response.ts:61도 매 회차 동일한 전체 종목 리스트를 넘긴다. 하지만 기존 테스트들(compute-home-summary.test.ts:48,63,77,89-90)은 이미 각 회차마다 테스트 작성자가 직접 고른 서로 다른 events 배열을 computeSessionRankings에 넘겨 SessionRankings 픽스처를 만드는 패턴을 쓰고 있다 — 그래서 #113의 실제 구현 완료 여부와 무관하게, "과거 4종목·최신 7종목" 상황을 오늘 당장 픽스처로 재현할 수 있다. 이슈에서 "#113과 병렬/독립"이라 명시한 이유가 바로 이것.

3설계

computeSessionRankings(session, events, players)를 회차마다 다른 events 배열로 두 번 호출해 "과거 회차엔 있었지만 최신 회차엔 없는 종목"이 이미 반영된 SessionRankings[]를 만든 뒤, 이 배열을 computeHomeSummary(sessions, rankings, players)에 넘겨 결과를 검증한다 — 기존 5개 테스트와 동일한 패턴(로컬 빌더 함수 재사용, 공유 픽스처 모듈 없음)이라 새 인프라가 필요 없다.

  • 혼재 픽스처: 과거 회차엔 4종목 배열, 최신 회차엔 7종목 배열(과거 4종목 중 일부를 포함해도 되고 완전히 겹치지 않아도 됨 — 이슈 문구가 "과거 4·최신 7"이라 개수만 맞추면 충분)을 넘겨 computeSessionRankings를 두 번 호출.
  • 종료 종목 소멸: 과거 회차 events 배열에는 있고 최신 회차 events 배열에는 빠진 종목 하나를 지정 — PRD §08의 "종료 종목은 최신 회차에 나타나지 않으므로 게이지에서 자연 소멸" 시나리오를 그대로 재현.
  • 두 테스트 모두 achievementRates의 길이와 event 키 집합을 단언해 "최신 회차 종목만, 과거 전용 종목은 전혀 없음"을 직접 증명한다 — 값(달성률 숫자)은 기존 테스트가 이미 충분히 덮고 있으므로 여기선 종목 구성만 집중.
  • 기각한 대안: SessionRankings를 손으로 직접 조립(리터럴 객체)하는 방법도 가능하지만, 기존 테스트 전원이 computeSessionRankings를 통해 만드는 컨벤션을 따르는 편이 일관되고, 나중에 #113이 실제로 필터링을 구현해도 이 테스트들의 호출부는 그대로 유효하다.

4작업 단계

  1. 혼재 픽스처(과거 4종목 · 최신 7종목) 회귀 테스트 추가 — 과거 회차를 4종목 events 배열로, 최신 회차를 7종목 events 배열로 각각 computeSessionRankings 호출해 SessionRankings[]를 만들고, computeHomeSummary 결과의 achievementRates가 정확히 최신 7종목만(길이 7, 과거 전용 종목 키 없음) 담는지 단언. functions/lib/compute-home-summary.test.ts
  2. 종료 종목 자연 소멸 회귀 테스트 추가 — 과거 회차 events엔 있지만 최신 회차 events엔 없는 종목 하나를 지정하고, achievementRates.find(r => r.event === '<해당 종목>')가 undefined임을 단언(에러나 0-엔트리 항목이 아니라 항목 자체가 없어야 함). functions/lib/compute-home-summary.test.ts
  3. 전체 스위트 실행해 기존 5개 + 신규 2개 = 7개 테스트 전원 그린 확인, 회귀 없음 확인. functions/lib/compute-home-summary.test.ts 실행 결과: compute-home-summary.test.ts + compute-rankings.test.ts 25개 통과, 전체 스위트(83 파일) 683개 통과, tsc -b 타입체크 그린.

5리스크

리스크영향완화책
#113(compute-rankings 회차별 순회)이 아직 미구현이라 프로덕션에서 이 좁혀짐이 실제로 일어나지 않음 테스트가 "이상적인 미래 입력"만 검증하고 오늘의 실제 파이프라인 동작은 못 잡아낼 수 있음 범위 밖(#113 소관) — #115는 "입력이 이미 좁혀졌다는 가정 하의 computeHomeSummary 동작"만 못박는 게 목적이라 이슈 문구와 일치. #113이 랜딩되면 이 테스트들은 자동으로 실제 파이프라인 검증으로 전환됨
손으로 만든 events 배열이 실제 computeSessionRankings 출력 형태와 어긋날 가능성 테스트가 실제와 다른 것을 검증할 위험 기존 5개 테스트와 동일하게 computeSessionRankings를 실제로 호출해 SessionRankings를 만들므로(직접 리터럴 조립 아님) 형태 어긋남 위험 없음

6테스트 계획

  • npx vitest run functions/lib/compute-home-summary.test.ts — 기존 5개 + 신규 2개 = 7개 전원 통과.
  • 신규 테스트 1: 혼재 픽스처 — achievementRates.length === 7이고 과거 전용 4종목 중 최신에 없는 종목의 키가 결과에 없어야 함.
  • 신규 테스트 2: 종료 종목 소멸 — 특정 종목 키로 find했을 때 undefined.
  • 회귀 확인: npx vitest run functions/lib/compute-rankings.test.ts도 함께 실행해 인접 모듈에 영향 없음 확인(코드 변경이 없으므로 그린이어야 정상).
