#162버그 수정

/api/records 캐시 계층 분리 — 브라우저 no-store, 엣지 사본만 max-age

damdam6/bernice 브랜치 fix/162-records-cache-layer-split ← main 라벨 bug 2026-07-28

1요약

functions/api/records.ts는 지금 하나의 응답을 엣지 Cache API 저장 사본과 클라이언트 응답 양쪽에 그대로 쓴다. 그래서 엣지 TTL 용도로 붙인 Cache-Control: public, max-age=21600이 브라우저까지 흘러가 /api/records를 6시간 동안 브라우저가 자체 캐시한다. 관리자 저장 성공 후 useSubmitMutation이 invalidate refetch를 걸어도 그 요청이 네트워크에 닿지 않고 브라우저 HTTP 캐시에서 옛 응답을 재사용하는 것이 스테일 증상의 주원인이다.

수정은 헤더 계층을 분리하는 것뿐이다 — 엣지에 cache.put하는 사본은 public, max-age=TTL을 유지하고(그래야 Cache API가 저장·TTL 계산을 한다), 클라이언트로 나가는 응답은 미스·히트 두 경로 모두 no-store로 교체한다. 캐시 키·TTL 상수, 무효화 경로(/api/refresh, 관리자 쓰기)는 건드리지 않는다.

2현황 분석

  • 미스 경로 — functions/api/records.ts:25-30: Response.json(body, { headers: { 'Cache-Control': `public, max-age=${RECORDS_CACHE_TTL_SECONDS}` } })로 응답 하나를 만들어 cache.put(cacheKey, response.clone())로 저장하고 같은 객체를 그대로 return한다. 저장 사본과 클라이언트 응답의 헤더가 동일할 수밖에 없는 구조다.
  • 히트 경로 — functions/api/records.ts:19-20: cache.match가 돌려준 응답을 return cached로 무가공 반환한다. 저장 시점에 박힌 max-age가 그대로 브라우저로 나간다.
  • TTL 상수 — functions/lib/records-cache.ts:12: RECORDS_CACHE_TTL_SECONDS = 60 * 60 * 6(6시간). 주석에도 이 값의 의도가 "무효화는 /api/refresh가 담당하므로 길게 잡는 엣지 캐시 수명"이라고 적혀 있다 — 브라우저 수명으로 의도된 값이 아니다.
  • 프론트 무효화 — src/hooks/useSubmitMutation.ts:77이 저장 성공 직후 invalidateQueries({ queryKey: RECORDS_QUERY_KEY, exact: true })를 await한다. TanStack Query는 refetch를 일으키지만, 실제 fetch('/api/records')(src/hooks/useRecords.ts:12, 기본 cache 모드)는 브라우저 HTTP 캐시에서 신선한(max-age 이내) 엔트리를 발견하면 네트워크로 나가지 않는다. 서버가 엣지 캐시를 지웠는지와 무관하게 화면이 옛 데이터를 본다.
  • 서버측 무효화는 이미 정상 — functions/api/refresh.ts:8과 관리자 쓰기 경로가 같은 RECORDS_CACHE_KEY로 cache.delete를 호출한다. 즉 엣지는 이미 즉시 무효화되는데 브라우저 계층만 손댈 방법이 없는 상태다.
  • 우회로가 이미 존재한다는 방증 — #151의 "데이터 새로 고침" 버튼은 fetchRecords(signal, 'reload')(src/hooks/useRecords.ts:9-14)로 브라우저 HTTP 캐시를 명시적으로 우회해야만 했다. 응답이 애초에 no-store였다면 필요 없었을 우회다(버튼 자체는 엣지 캐시 갱신 목적도 있어 유지).
  • 테스트 현황 — functions/api/records.test.ts:77이 클라이언트 응답의 Cache-Control에 /max-age=\d+/를 어서션한다. 저장 사본(put.mock.calls[0][1])에 대한 어서션은 없고, 히트 경로 테스트(:87-100)도 헤더를 보지 않는다. 즉 지금 계약을 고정하는 어서션이 정확히 뒤집어야 할 그 한 줄이다.

3원인 분석

근본 원인: "엣지 저장 사본의 TTL"과 "클라이언트에게 알리는 캐시 정책"이 같은 Cache-Control 헤더 하나로 표현돼 있다. Cache API는 저장할 응답의 Cache-Control로 TTL을 정하므로 저장 사본에는 max-age가 반드시 필요하고(no-store 사본은 저장이 거부된다), 브라우저는 같은 헤더를 자기 캐시 지시로 읽는다. 하나의 응답 객체를 두 소비자가 공유하는 한 이 충돌은 피할 수 없다.

설계 — 응답을 두 갈래로 나눈다. 저장용 응답은 지금 그대로 public, max-age=TTL, 반환용 응답은 그 사본의 Cache-Control만 no-store로 바꾼 복제본. 히트 경로도 같은 변환을 태워 클라이언트가 보는 헤더는 두 경로에서 동일하게 만든다.

// 클라이언트로 나가는 응답은 미스·히트 모두 no-store — 엣지 저장 사본(max-age)과 분리한다.
// cache.match가 돌려준 응답은 헤더가 immutable이라 new Response(body, init)로 복제해야 교체할 수 있다.
function withNoStore(response: Response): Response {
  const copy = new Response(response.body, response)
  copy.headers.set('Cache-Control', 'no-store')
  return copy
}

// 히트
const cached = await cache.match(cacheKey)
if (cached) return withNoStore(cached)

// 미스
const response = Response.json(body, {
  headers: { 'Cache-Control': `public, max-age=${RECORDS_CACHE_TTL_SECONDS}` },
})
context.waitUntil(cache.put(cacheKey, response.clone()))  // 저장 사본: max-age 유지
return withNoStore(response)                              // 클라이언트: no-store
  • 왜 new Response(response.body, response)인가 — Cache API가 돌려준 응답의 헤더는 immutable 가드라 headers.set이 던진다. 이 이디엄이 status·statusText·헤더를 그대로 복사하면서 헤더만 mutable로 만드는 표준 방식이다. 미스 경로도 같은 헬퍼를 태워 경로별 분기 없이 한 곳에서 계약을 보장한다(clone()을 먼저 뜬 뒤 감싸므로 본문 스트림 충돌 없음).
  • 기각 1 — 반환용 응답을 Response.json(body, …)으로 한 번 더 만들기: 같은 페이로드를 두 번 직렬화하고, 히트 경로에서는 어차피 쓸 수 없어(본문만 있고 body 객체가 없다) 경로별로 다른 코드가 된다.
  • 기각 2 — TTL 상수를 0/짧게 줄이기: 엣지 캐시의 존재 이유(시트 API 호출 절감)를 없앤다. 문제는 TTL 값이 아니라 그 값이 브라우저에까지 적용되는 것.
  • 기각 3 — 프론트에서 cache: 'no-store'로 항상 우회: 증상은 가려지지만 서버가 여전히 "6시간 캐시해도 된다"고 거짓 계약을 내보낸다. 다른 소비자(직접 호출·프리페치·프록시)에 그대로 남는 문제라 서버에서 고치는 게 맞다.
  • 스코프 밖(그대로 둔다): RECORDS_CACHE_KEY/TTL 상수, /api/refresh와 관리자 쓰기의 cache.delete, #151 새로 고침 버튼의 'reload'(엣지 갱신 목적으로 여전히 유효), 콜로 로컬 무효화 한계.

  2. 미스 경로 분리. cache.put에는 max-age를 유지한 response.clone()을 그대로 넘기고(순서 유지: clone → put → wrap), return만 withNoStore(response)로 바꾼다. 헤더의 두 용도를 설명하는 주석을 갱신한다. functions/api/records.ts
  3. 단위 테스트 갱신. 미스 테스트: :77의 max-age 어서션을 no-store로 바꾸고, 저장 사본 cache.put.mock.calls[0][1].headers에 public, max-age=${RECORDS_CACHE_TTL_SECONDS} 어서션을 추가한다(TTL 상수를 import해 하드코딩 회피). 히트 테스트: 응답 Cache-Control이 no-store이고 본문(events)이 미스 때와 동일하게 읽히는지(복제가 본문을 깨지 않는지) 어서션을 추가한다. 테스트 제목도 계층 분리를 드러내게 손본다. functions/api/records.test.ts

5리스크

리스크영향완화책
no-store가 저장 사본에 섞여 들어가면 Cache API가 저장을 거부 엣지 캐시가 사실상 무력화 → 매 요청 시트 API 호출(할당량·지연) 순서를 고정한다: clone() → cache.put → 그 다음에 반환용 복제본만 헤더 교체. 저장 사본 헤더를 put.mock.calls[0][1]로 직접 어서션해 회귀를 테스트로 못 박는다
new Response(res.body, res)가 본문 스트림을 소모/잠글 가능성 히트 경로 응답 본문이 비거나 json()이 던짐 미스 경로는 clone()을 먼저 떠서 독립 스트림을 확보. 히트·미스 양쪽에서 본문(events)을 읽는 어서션을 두고, e2e 스모크가 clone().json()으로 한 번 더 검증
브라우저 캐시가 사라져 매 진입마다 /api/records 왕복 네트워크 요청 증가 의도된 변경. 엣지 캐시가 그대로라 원본(시트) 호출은 늘지 않고, 프론트는 TanStack Query staleTime: 5분(src/hooks/useRecords.ts)이 세션 내 재조회를 이미 억제한다
이미 max-age 응답을 받아 둔 브라우저는 배포 후에도 최대 6시간 스테일 배포 직후 일부 사용자에게 증상이 남아 "안 고쳐졌다"로 보임 새 응답을 한 번 받으면 항구적으로 해소. 그 사이엔 #151 "데이터 새로 고침" 버튼(cache: 'reload')이 즉시 우회로가 된다 — PR 본문에 명시

6테스트 계획

  • 미스 경로 (회귀): functions/api/records.test.ts — 반환 응답 Cache-Control === 'no-store', 동시에 cache.put에 넘긴 사본은 public, max-age=21600. 두 어서션이 한 테스트에 있어야 "분리"가 실제로 검증된다.
  • 히트 경로 (회귀): cache.match가 max-age 사본을 돌려줘도 반환 응답은 no-store. 기존 "히트 시 fetchSheetBundle을 호출하지 않는다" 어서션은 유지.
  • 본문 무결성: 히트 응답의 events가 미스 응답과 동일 — new Response(body, init) 복제가 페이로드를 손상시키지 않음을 확인.
  • 기존 동작 유지: 에러 매핑 3종(502 sheets_api_error · 500 missing_roster_tab · 500 sheet_data_invalid)은 캐시 헤더와 무관하게 그대로 통과.
