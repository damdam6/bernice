#113기능 개선

P7 — compute-rankings: 회차별 측정 종목만 순회

damdam6/bernice 브랜치 feat/113-compute-rankings-eventkeys-only ← main 라벨 enhancement 2026-07-27

1요약

computeSessionRankings는 지금 events[](목표 탭 전체 종목)를 그대로 순회해, 그 회차에 측정하지 않은 종목도 entries: []로 채워 반환한다. #110에서 Session.eventKeys와 SessionRankings.events의 계약(그 회차 측정 종목만, 미측정 종목×회차 조합은 항목 자체가 없음)이 이미 확정됐지만, 구현은 아직 옛 규칙 그대로다. 이번 이슈는 compute-rankings.ts 한 파일만 그 계약을 따라잡는다 — computeEventRanking(종목 1개 랭킹 로직)은 손대지 않는다.

2현황 분석

functions/lib/compute-rankings.ts:67-74 현재 구현:

/** 회차 1개에 대한 종목별 랭킹 묶음. 엔트리가 0건인 종목도 entries: []로 유지해
 *  events[] 전체와 개수를 맞춘다(프론트 종목 탭이 회차마다 사라지지 않도록). */
export function computeSessionRankings(session: Session, events: EventDefinition[], players: Player[]): SessionRankings {
  return {
    sessionDate: session.date,
    events: events.map((event) => computeEventRanking(event, session.entries, players)),
  }
}

주석(67-68행)부터가 지금 shared/domain.ts:95-96의 SessionRankings.events 계약 주석과 정면으로 모순된다: 도메인 타입은 "그 회차 Session.eventKeys에 해당하는 종목만... 빈 종목도 entries: []로 개수 맞추던 규칙은 폐기"라고 이미 개정됐다(ecb4084, #130). 즉 계약은 바뀌었고 구현만 남았다.

유일한 프로덕션 호출부는 functions/lib/build-records-response.ts:61: sessions.map((session) => computeSessionRankings(session, events, players)) — 여기서 events는 parseGoals가 만든 종료 종목 포함 전체 목록이다. 이 호출부는 그대로 두면 된다: computeSessionRankings가 내부에서 session.eventKeys 기준으로 좁히는 게 이번 수정의 핵심이라, 호출부는 계속 전체 events를 넘기고 함수가 알아서 걸러야 한다.

다운스트림 소비자 computeHomeSummary(같은 호출부, functions/lib/compute-home-summary.ts:23 latestRankings.events.map(...))는 SessionRankings.events가 좁혀지면 자동으로 좁혀진 입력을 받는다 — PRD §07이 명시한 대로 이 파일은 무변경. 그 회귀 테스트 보강은 별도 이슈(#115) 몫이다.

computeEventRanking(21-65행)은 이미 entry.scores[event.key]를 optional chaining으로 접근한다(39-40행) — eventKeys 밖의 종목이 넘어와도 score?.status !== 'recorded'로 안전하게 걸러지므로, 이 함수 자체는 무변경으로 둬도 된다. (참고: player-summary.ts:40의 동일 패턴은 optional chaining 없이 직접 접근해 TypeError 위험이 있는데, 이는 이슈 #114의 스코프다 — 이번 이슈에서 건드리지 않는다.)

기존 테스트 functions/lib/compute-rankings.test.ts:266-280("여러 종목이 있으면 각 종목이 events 배열 순서·개수 그대로 독립적으로 계산된다")는 사실 옛 규칙을 검증하는 테스트다: eventKeys: ['A', 'B']인 세션에서 종목 B가 전원 미측정이어도 entries: []로 포함되길 기대한다(279행). 이 케이스는 "측정은 했는데 아무도 기록 안 함"이라 eventKeys 안에 있으므로 새 규칙에서도 여전히 유효하다 — 하지만 "애초에 그 회차 eventKeys에 없는 종목"은 지금 테스트 스위트에 전혀 없다. 이슈의 완료 조건이 요구하는 케이스(4종목 회차 + 7종목 회차 혼재)는 새로 추가해야 한다.

3설계

채택: events: EventDefinition[]에서 key → EventDefinition 맵을 만들고, session.eventKeys(헤더 순서)를 순회하며 각 key로 맵을 조회해 computeEventRanking을 호출한다. 결과 배열은 eventKeys 순서·길이와 정확히 대응한다.

export function computeSessionRankings(session: Session, events: EventDefinition[], players: Player[]): SessionRankings {
  const eventsByKey = new Map(events.map((event) => [event.key, event]))
  return {
    sessionDate: session.date,
    events: session.eventKeys
      .map((key) => eventsByKey.get(key))
      .filter((event) => event !== undefined)
      .map((event) => computeEventRanking(event, session.entries, players)),
  }
}

eventKeys에 있는데 events에 없는 key를 어떻게 할까: 조용히 건너뛴다(filter로 제거). 계약상 파서(#111/#112)가 이 불변식을 보장하지만, #113은 "Session 픽스처로 병렬 개발"(이슈 명시)하므로 파서 완성을 기다리지 않는다 — 존재하지 않는 종목 정의를 참조하는 방어적 처리가 필요하다. throw로 실패시키는 대안은 기각: 계산 함수가 파서의 불변식 위반을 새로 검증하는 책임을 지면 관심사가 섞이고, 이슈 범위(§07 표)에도 없다.

기각한 대안 — Map 없이 events.filter(e => session.eventKeys.includes(e.key)): 순서가 events(목표 탭 행 순서)를 따르게 되어 eventKeys(그 회차 헤더 순서) 요구사항을 어긴다. §06 계약이 "헤더 순서"를 명시하므로 eventKeys.map이 맞다.

67-68행의 주석도 새 계약을 설명하도록 다시 쓴다(옛 "개수를 맞춘다" 표현 제거).

4작업 단계

  1. computeSessionRankings(functions/lib/compute-rankings.ts:67-74)를 session.eventKeys 기준 순회로 다시 쓰고, 67-68행 주석을 새 계약(§06)에 맞게 갱신한다. functions/lib/compute-rankings.ts
  2. 기존 describe('computeSessionRankings', ...) 스위트(compute-rankings.test.ts:208-281)에 새 픽스처를 추가: (a) 4종목 eventKeys 세션과 7종목 eventKeys 세션을 같은 events(그 둘의 합집합, 예: 8~9종목 슈퍼셋) 배열로 각각 computeSessionRankings 호출 → 각 결과의 events 길이·event key 목록이 그 세션의 eventKeys와 정확히 일치하고 순서도 eventKeys 순서를 따르는지 검증. (b) eventKeys에 없는 종목이 events에 있을 때 결과에서 완전히 빠지는지(entries: [] 조차 아니라 항목 자체 부재) 단언. functions/lib/compute-rankings.test.ts 실제로는 세 개의 신규 it로 나눠 추가: (a) 4/7종목 혼재 순회, (b) eventKeys 밖 종목의 완전 부재, (c) 계획에 없던 추가 방어 테스트 — eventKeys에는 있지만 목표 탭(events)에는 정의가 없는 key도 조용히 제외되는지.
  3. 기존 두 테스트(209행 §06 예시 응답, 266행 "여러 종목") 그대로 둔다 — 둘 다 eventKeys가 이미 새 필드로 채워져 있고 새 구현에서도 그대로 통과해야 한다. 실행해서 실제로 그린인지 확인. functions/lib/compute-rankings.test.ts
  4. computeEventRanking 테스트(31-206행, 15개 it)는 무수정 상태로 전부 그린이어야 한다 — 별도 변경 없음, 실행 결과만 확인. functions/lib/compute-rankings.test.ts
  5. 전체 테스트·타입체크 실행(npm test, npm run typecheck)해 compute-home-summary.test.ts 등 computeSessionRankings를 픽스처 헬퍼로 쓰는 다른 스위트가 깨지지 않는지 확인. 깨지면 그 스위트가 옛 "빈 종목 유지" 동작에 의존했다는 뜻이므로 그 픽스처만 새 계약에 맞게 고친다(스코프 벗어난 로직 변경은 하지 않는다). functions/lib/compute-home-summary.test.ts 실제로는 픽스처 조정 불필요 — 전체 83개 테스트 파일·684개 테스트가 무수정 상태로 그린이었다.

5리스크

리스크영향완화책
