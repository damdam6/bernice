P7 — ranking-view: 회차별 종목 파생·가드

damdam6/bernice 브랜치 feat/116-ranking-view-session-events-guard ← main 라벨 enhancement 2026-07-27

1요약

buildRankingRows(src/lib/ranking-view.ts)가 회차 원본 session.entries를 순회하며 entry.scores[eventKey]를 undefined 방어 없이 읽는다. 그 회차에 측정되지 않은 종목으로 호출되면 score.status 접근에서 크래시한다. #114(player-summary, PR #131)와 같은 패턴의 한 줄 가드(if (!score) continue)를 추가하고, 혼재 회차·undefined 두 시나리오를 픽스처 테스트로 고정한다. findTiedRanks·buildEventGuidance는 변경하지 않는다.

2현황 분석

buildRankingRows(src/lib/ranking-view.ts:14-39)는 종목 1개·회차 1개의 표시용 행을 만든다. 순위권 엔트리(eventRanking.entries)를 그대로 옮긴 뒤, 그 회차 session.entries를 순회하며 아직 순위권에 없는 활동 선수를 면제·미측정·이상값으로 하단에 보충한다(ranking-view.ts:26-36).

보충 루프의 핵심 줄은 ranking-view.ts:29 — const score = entry.scores[eventKey]를 undefined 방어 없이 바로 score.status로 분기한다(30·32행). shared/domain.ts:62-63의 신계약(#110)상 SessionEntry.scores는 "그 회차 Session.eventKeys 전체가 항상 존재, 그 외 key는 없음"이라 eventKey가 그 회차 측정 종목이 아니면 entry.scores[eventKey]는 undefined이고 score.status 접근은 TypeError로 크래시한다.

이 경로는 이론상으로만 존재하지 않는다. 호출부 src/pages/Rankings.tsx:56-58은 rankings[].events[].event === eventKey로 eventRanking을 찾은 뒤, 찾아지면(=undefined가 아니면) 바로 buildRankingRows를 호출한다. 그 eventRanking을 만드는 computeSessionRankings(functions/lib/compute-rankings.ts:69-74)는 아직 "회차별 순회"로 스코핑되지 않고 모든 종목에 대해 EventRanking을 만든다 — PRD(docs/prd-event-lifecycle.html §13 표 항목3 "계산 — 랭킹·추이·홈 회차별 대응")가 별도 이슈로 예정해둔 작업이라 이번 스코프가 아니다. 즉 오늘 기준으로도 어떤 종목이 특정 회차에서 미측정이면 eventRanking은 entries: []로나마 "찾아지고", buildRankingRows가 그 회차 session.entries를 순회하다 scores[eventKey]가 없는 엔트리를 만나 크래시할 수 있다.

같은 모양의 결함이 functions/lib/player-summary.ts에도 있었고 #114(PR #131)에서 if (!score) continue 한 줄 가드로 고쳤다. functions/lib/compute-rankings.ts:39도 이미 score?.status !== 'recorded' optional chaining으로 같은 자리를 방어하고 있다 — ranking-view.ts만 이 가드가 빠져 있다.

현재 src/lib/ranking-view.test.ts의 모든 픽스처(35-108행)는 session.eventKeys: [EVENT_KEY]이고 모든 sessionEntry가 그 키의 점수를 갖고 있어 이 경로가 테스트되지 않는다.

3원인 분석

#114와 동일한 패턴을 그대로 적용한다 — ranking-view.ts:29 다음 줄에 if (!score) continue를 추가해 그 선수를 조용히 건너뛴다(별도 상태를 만들지 않음 — 크래시 대신 "표시 안 함"이 안전한 기본값).

대안으로 고려했으나 기각:

  • 함수 진입부에서 session.eventKeys.includes(eventKey)를 먼저 검사 — scores[eventKey] === undefined 검사와 결과가 동일하고, 매개변수 하나(session.eventKeys)를 추가로 신뢰해야 해 계약 표면만 늘어난다. entry 단위 undefined 체크가 실제 접근 지점에서 더 직접적으로 방어한다.
  • score가 없는 선수를 별도 RankingRowDatum 상태(예: 'not-tracked')로 노출 — 이슈 범위(#116)가 "크래시 대신 안전 동작"만 요구하고 UI 상태 확장은 요구하지 않는다. 정상 경로(호출부가 측정 종목만 넘기는 것이 최종 목표)에서는 이 분기에 도달하지 않으므로 새 상태를 노출할 필요가 없다.

findTiedRanks·buildEventGuidance는 eventKeys나 scores를 전혀 참조하지 않는다 — 각각 rows의 status/rank만(41-49행), EventDefinition 필드만(58-63행) 사용해 이번 변경과 무관하다. 이슈 원문의 "불변" 조건 그대로 둔다.

4작업 단계

  1. buildRankingRows 보충 루프에 undefined 가드 추가 — const score = entry.scores[eventKey] 다음 줄에 if (!score) continue. 35행의 "recorded는 도달 불가" 주석도 이 케이스(계약 위반 시 score 자체가 undefined)를 함께 언급하도록 보강. src/lib/ranking-view.ts
  2. "미측정 종목 가드" describe 블록 추가 — (a) 대상 eventKey가 그 회차 eventKeys에 아예 없는 세션(다른 종목만 측정)으로 호출 시 크래시 없이 빈 배열을 반환하는지, (b) 한 회차에 종목 2개가 혼재할 때 보충 행이 호출한 eventKey 하나에 대해서만(다른 종목의 상태와 무관하게) 정확히 생성되는지 검증. #114의 player-summary.test.ts와 같은 결(공유 픽스처 + 복수 it)로 작성. src/lib/ranking-view.test.ts
  3. npm run typecheck · npm run test로 전체 스위트 회귀 없음 확인.

5리스크

리스크영향완화책
가드 추가가 기존 동작을 바꿀 가능성낮음 — 기존 ranking-view.test.ts 픽스처는 전부 scores[eventKey]가 존재해 새 가드 분기에 진입하지 않음npm run test로 기존 5개 buildRankingRows 테스트 그대로 통과 확인
computeSessionRankings가 아직 회차별로 스코핑되지 않아(PRD §13 항목3, 별도 이슈) eventRanking이 미측정 종목에도 만들어짐이번 이슈 범위 밖이지만 실제 크래시 재현 경로 — 이 가드 없이는 오늘도 도달 가능이번 가드로 즉시 방어. 근본 스코핑(회차별 순회)은 항목3 이슈에서 별도 처리
