E2E — 관리자 쓰기 직후 GET /api/records 최신성 회귀망

damdam6/bernice 브랜치 feat/165-e2e-write-freshness ← main 라벨 enhancement 2026-07-28

1요약

쓰기 3종(admin/records · create-sheet · add-players)이 응답을 돌려준 바로 그 순간 같은 캐시를 공유하는 GET /api/records가 이미 최신 데이터를 반환하는지를 고정하는 통합 회귀망을 새로 만든다. 기존 records.e2e.test.ts는 GET 계약만 스모크하고, 각 핸들러 단위 테스트는 "cache.delete가 불렸다"까지만 본다 — 무효화가 실제로 다음 조회의 데이터를 바꾸는지는 아무도 검증하지 않아 #161(create-sheet waitUntil) 같은 회귀가 통과했다.

핵심 장치는 세 개다. ① 읽기·쓰기 핸들러가 같은 가변 시트 스토어를 공유하게 해 쓰기가 다음 읽기에 실제로 보이게 하고, ② waitUntil을 지연 큐로 만들어 쓰기 응답과 후속 GET 사이에 flush를 하지 않으며, ③ fake Cache가 no-store 응답 put을 실제 Workers Cache API처럼 거부해 헤더 계층 분리(#162)까지 같은 시나리오에서 어서션한다.

2현황 분석

현재 캐시 파이프라인 (T1·T2 머지 후 상태)

  • functions/lib/records-cache.ts:9 — 고정 합성 키 https://bernice-cache.internal/records/v2, TTL 21600초. purgeRecordsCache()(records-cache.ts:17)가 caches.default.delete()의 단일 창구다.
  • functions/api/records.ts:19-34 — GET는 cache.match 히트면 그대로, 미스면 fetchSheetBundle → buildRecordsResponse로 조립한다. 저장 사본은 public, max-age=21600을 단 clone이고(records.ts:33), 클라이언트로 나가는 응답만 withNoStore()로 no-store가 된다(records.ts:44-48). put은 context.waitUntil에 실린다.
  • 쓰기 3종은 모두 응답 전 await purgeRecordsCache(): functions/api/admin/records.ts:125 · create-sheet.ts:92 · add-players.ts:88. #161에서 create-sheet만 waitUntil이었던 것을 await로 통일했다.

현재 테스트가 덮는 범위와 구멍

  • functions/api/records.e2e.test.ts — GET 전 구간 계약 스모크. makeFakeCache()는 match/put만 있고 delete가 없으며(:87-98), makeContext()의 waitUntil은 no-op이라 put이 아예 유실된다(:103). 매 요청마다 새 캐시를 만들어(:114) 캐시 히트 경로 자체가 실행되지 않는다.
  • 핸들러 단위 테스트(admin/create-sheet.test.ts:38-46, add-players.test.ts:41-58)는 caches.default를 {delete}만 있는 스텁으로 세우고 "delete가 RECORDS_CACHE_KEY로 1회 호출됐다"를 본다. 삭제 호출은 잡지만, 삭제된 캐시가 다음 GET의 데이터를 바꾸는지는 못 잡는다.
  • 결국 쓰기 핸들러와 GET 핸들러가 한 테스트 안에서 같은 캐시·같은 시트를 공유한 적이 한 번도 없다 — 이슈가 요구하는 통합 시나리오가 정확히 이 빈칸이다.

3설계

새 파일 1개 — functions/api/records-invalidation.e2e.test.ts(이슈가 제안한 이름). 기존 records.e2e.test.ts는 GET 계약 스모크라는 역할이 뚜렷해 건드리지 않고, 인접 신규 파일로 둔다.

① 가변 fake 시트 스토어 (이 설계의 핵심)

  • Map<탭이름, {sheetId, values: string[][]}> 하나를 세워, 읽기 목(fetchSheetBundle · getSpreadsheetSheets · getSpreadsheetTabTitles · batchGetValues)과 쓰기 목(updateValues · batchUpdate)이 같은 스토어를 보게 한다. 쓰기가 스토어를 실제로 바꾸므로 다음 읽기가 새 데이터를 본다 — "쓰기→조회 최신성"을 검증하려면 이 가변성이 없으면 안 된다.
  • 수식 해석: add-players는 A열에 ='버니스명단'!A7, create-sheet는 헤더에 =목표!A3을 쓴다. 실제 API는 FORMATTED_VALUE로 평가된 값을 돌려주므로, fake도 읽기 시점에 단일 셀 참조(='탭'!A{행})를 스토어에서 해석한다. 그래야 새 참가자 이름이 parse-session의 이름 매칭에 걸린다.
  • 모킹 층위: fetchSheetBundle은 getSpreadsheetTabTitles/batchGetValues를 모듈 내부 로컬 바인딩으로 호출하므로, 그 둘만 목킹해도 가로채이지 않는다 → fetchSheetBundle도 직접 목으로 대체하되 실제 classifySheetTabs를 재사용해 조립 규칙이 갈라지지 않게 한다. (대안: fetch+googleAuth까지 내려가 진짜 HTTP 백엔드를 흉내내기 — JWT 서명·URL 파싱까지 떠안아야 해 이 레포의 확립된 "I/O 경계만 목킹" 관용구(create-sheet.test.ts:3)에서 벗어난다. 기각.)

② 지연 waitUntil 큐 — 회귀를 물게 만드는 장치

  • makeContext()의 waitUntil은 no-op도, 즉시 await도 아닌 큐에 담고 flush()에서만 await한다. 시나리오는 ① GET → flush()(캐시 적재) → ② 쓰기 POST → flush 없이 ③ GET.
  • 누군가 await purgeRecordsCache()를 waitUntil(purgeRecordsCache())로 되돌리면(=#161 회귀) 무효화가 큐에 남은 채 ③이 실행돼 옛 캐시가 히트하고, 테스트는 옛 데이터로 실패한다. no-op waitUntil이었다면 이 회귀가 오히려 조용히 통과해버린다 — 지연 큐가 필수인 이유.
  • 단, 지연 큐만으로는 부족하다(구현 중 확인). fake Cache의 delete가 효과를 호출 즉시 적용하면 — async 함수 본문은 첫 await 전까지 동기 실행되므로 — 무효화가 큐에 실려 있든 아니든 이미 삭제가 끝나 있어 두 경우가 구분되지 않는다. 그래서 put·delete의 효과를 다음 매크로태스크로 미룬다(afterIo()): 실제 Cache API처럼 호출한 틱 안에 끝나지 않으므로, await한 핸들러만 응답 전에 반영되고 waitUntil에만 실은 핸들러는 반영되지 않는다.

③ 헤더 계층 분리(#162) 어서션을 같은 시나리오에 합류

  • fake Cache의 put이 Cache-Control: no-store 응답을 거부한다(실제 Workers Cache API 동작). records.ts가 clone/no-store 순서를 뒤집으면 저장이 거부돼 캐시 히트 경로가 사라지고, "두 번째 GET는 시트를 다시 읽지 않는다" 어서션이 깨진다.
  • 직접 어서션: 클라이언트 응답은 미스·히트 모두 no-store, put에 넘어간 사본은 public, max-age=21600(RECORDS_CACHE_TTL_SECONDS 상수에서 도출 — 하드코딩 금지).

픽스처: 이 파일은 전 계약이 아니라 최신성을 보므로, records.e2e.test.ts의 8종목 실시트 픽스처를 복제하지 않고 명단 7명 · 목표 3종목 · 회차 1개짜리 최소 픽스처를 새로 세운다. 대신 쓰기 결과가 응답 어느 필드에 나타나는지를 정확히 짚는다(sessions[].entries[].scores · rankings · sessions[].date).

4작업 단계

  1. 가변 fake 시트 스토어 작성 — 탭 Map + 읽기 4종 목 + 단일 셀 참조 수식 해석. 실제 classifySheetTabs로 번들 조립. functions/api/records-invalidation.e2e.test.ts
  2. 쓰기 적용기 작성 — updateValues의 A1 범위 파싱('탭'!B7:E7)과 batchUpdate의 addSheet/updateCells 적용. functions/api/records-invalidation.e2e.test.ts
  3. 공유 하네스 — match/put/delete를 갖고 no-store put을 거부하는 fake Cache, 지연 waitUntil 큐를 가진 makeContext(), getRecords() 헬퍼. functions/api/records-invalidation.e2e.test.ts 설계 보강(단계 8에서 발견): 지연 waitUntil 큐만으로는 회귀가 잡히지 않았다. fake Cache의 put·delete가 효과를 호출 즉시 적용하면(async 함수 본문은 첫 await 전까지 동기 실행된다) await purgeRecordsCache()와 waitUntil(purgeRecordsCache())가 구분되지 않는다. 두 작업의 효과를 다음 매크로태스크로 미루는 afterIo()를 추가해 await한 핸들러만 응답 전에 반영되게 했다. match는 일부러 미루지 않는다 — 밀려 있던 delete가 그 틈에 실행돼 오히려 회귀를 가린다.
  4. 시나리오 A — POST /api/admin/records: GET로 캐시 적재 → 점수 저장 → flush 없이 GET가 바뀐 점수를 반환. functions/api/records-invalidation.e2e.test.ts, functions/api/admin/records.ts 계약 관통 테스트를 하나 더 붙였다 — 바뀐 점수가 rankings(골밑슛 1위가 다현→가은으로 교체)·trends·home까지 흐르는지.
  5. 시나리오 B — POST /api/admin/create-sheet: 캐시 적재 → 오늘 회차 생성(201) → flush 없이 GET에 새 세션이 등장(eventKeys·참가자 포함). 날짜는 fake timer로 고정. functions/api/records-invalidation.e2e.test.ts, functions/api/admin/create-sheet.ts fake timer는 toFake: ['Date']로 Date만 가짜로 돌린다 — setTimeout까지 멈추면 위 afterIo가 영영 끝나지 않아 await purgeRecordsCache()가 교착에 빠진다. 새 탭 셀이 참조 수식으로 쓰였는지(명단·목표 편집이 회차 탭에 자동 반영되는 운영 포맷) 확인하는 테스트도 추가.
  6. 시나리오 C — POST /api/admin/add-players: 캐시 적재 → 참가자 추가 → flush 없이 GET의 sessions[].entries에 새 이름 등장(수식 해석 경유). functions/api/records-invalidation.e2e.test.ts, functions/api/admin/add-players.ts
  7. 헤더 계약 어서션 — 미스·히트 응답 no-store, 저장 사본 public, max-age=21600, 히트 시 시트 재조회 없음. functions/api/records-invalidation.e2e.test.ts, functions/lib/records-cache.ts
  8. 회귀망 자체 검증 — 회귀 4종을 차례로 주입해 빨간불을 확인하고 전부 원복(커밋하지 않음). functions/api/admin/records.ts, functions/api/admin/create-sheet.ts, functions/api/admin/add-players.ts, functions/api/records.ts 결과: create-sheet waitUntil → 시나리오 B 2건 실패("2026-07-23 회차가 응답에 없습니다") · admin/records waitUntil → 시나리오 A 2건 실패(랭킹 1위가 옛 데이터인 다현으로 남음) · add-players waitUntil → 시나리오 C 실패 · records.ts의 no-store/clone 순서 뒤집기 → 7건 전부 실패 (fake Cache가 no-store 사본 저장을 거절). 첫 시도에서 아무것도 빨개지지 않은 것이 위 afterIo 보강의 계기였다.
  9. 전체 테스트 · 타입체크 실행 후 커밋 · 푸시 · PR. package.json npm test 87파일 804테스트 그린 · npm run typecheck(tsc -b --force 포함) 그린.
