#114버그 수정

P7 — player-summary: 미측정 회차 스킵 가드

damdam6/bernice 브랜치 feat/114-player-summary-unmeasured-skip-guard ← main 라벨 enhancement 2026-07-27

1요약

#110에서 SessionEntry.scores의 계약이 "events[] 전체 key가 항상 존재"에서 "그 회차 Session.eventKeys에 있는 key만 존재, 그 외 key는 아예 없음"으로 바뀌었다. player-summary.ts의 collectValidScores는 여전히 entry.scores[event.key]를 무가드로 읽고 바로 .status를 참조해서, 그 회차에 측정되지 않은 종목(신규 종목의 과거 회차, 종료 종목의 이후 회차, 측정 생략 회차)을 만나면 TypeError가 난다. 이미 존재하는 "entries 없는 세션은 조용히 스킵"(if (!entry) continue) 패턴과 동형으로 한 줄 가드를 추가하고, 이 경로를 실제로 밟는 테스트 픽스처를 새로 추가한다.

2현황 분석

호출 체인: functions/lib/build-records-response.ts:62의 buildRecordsResponse가 computePlayerSummaries(events, players, sessions)(functions/lib/player-summary.ts:93-111)를 호출하고, 이 함수는 활동 중인 선수마다 전체 events[](종료 종목 포함)를 순회하며 collectValidScores(player, event, sessions)(player-summary.ts:33-47)를 부른다.

버그 지점 — player-summary.ts:40-41:

const score = entry.scores[event.key]
if (score.status !== 'recorded') continue   // score가 undefined면 여기서 TypeError

계약 근거 — shared/domain.ts의 SessionEntry.scores 필드 주석(#110에서 개정): "key = EventDefinition.key. 그 회차 Session.eventKeys 전체가 항상 존재, 그 외 key는 없음 — 소비자는 scores[key] 인덱싱 전에 그 회차 측정 여부를 전제해야 한다." Session.eventKeys는 그 회차 탭 헤더의 측정 종목 key 목록이다.

docs/prd-event-lifecycle.html §07 표는 이 이슈와 1:1로 대응하는 행을 명시한다: "collectValidScores에 미측정 회차 스킵 가드 — entry.scores[event.key]가 없으면 건너뛴다(현행 코드는 여기서 TypeError). 'entries가 없는 세션(미가입)은 조용히 스킵'하는 기존 규칙과 동형. 추이·PB·델타 공식 불변 — 종료 종목도 과거 기록으로 동일 계산." §05 검증 매트릭스 V3 행: "목표 탭 종목이 회차 탭 헤더에 없음" → 정상, "그 회차 미측정"으로 취급 — 종목 추가(신규 종목의 과거 회차), 종목 종료(종료 이후 회차), 측정 생략(단발성 회차)이 모두 이 한 규칙으로 수용된다.

기존 방어 패턴 — player-summary.ts:38의 if (!entry) continue(엔트리 자체가 없는 세션 스킵)와, 같은 접근 지점을 이미 optional chaining으로 방어하고 있는 compute-rankings.ts의 computeEventRanking(const score = entry.scores[event.key]; if (score?.status !== 'recorded') continue) — 스타일 선례로 참고.

기존 테스트 — functions/lib/player-summary.test.ts의 모든 픽스처(SESSIONS, 경계값 블록 포함)는 매 세션의 eventKeys에 events[] 전체를 담고, 매 엔트리도 두 종목 모두에 대해 (unmeasured()이라도) 명시적인 EventScore를 채워 넣는다. 즉 현재 테스트 스위트는 entry.scores[event.key] === undefined 경로를 한 번도 밟지 않는다 — 이 이슈가 요구하는 픽스처 공백 그 자체.

3원인 분석

근본 원인: #110에서 SessionEntry.scores의 인덱스 보장 범위가 "전체 종목"에서 "그 회차 측정 종목만"으로 좁혀졌는데, collectValidScores는 이 계약 변경 전 가정(모든 키가 항상 존재)에 맞춰 작성된 채로 남아 있다. TypeScript의 Record<string, EventScore> 인덱스 시그니처는 noUncheckedIndexedAccess가 꺼져 있는 한 undefined를 타입에 노출하지 않으므로, 컴파일 타임에도 이 구멍이 잡히지 않는다.

대안 검토: (a) EventScore에 'unmeasured'류의 명시적 값을 항상 채워 넣도록 파서/응답 생성 쪽을 바꾸는 방법은 §06/§07이 이미 확정한 "키 자체가 없다"는 계약과 어긋나고 응답 페이로드도 불필요하게 커진다 — 채택하지 않음. (b) collectValidScores 진입부에서 event.key가 session.eventKeys에 포함되는지 먼저 확인하는 방법도 동작은 하지만, 실제로 크래시를 내는 지점(스코어 접근)에서 한 줄로 막는 게 더 직접적이고 기존 if (!entry) continue 패턴과 형태가 맞는다 — 이걸 채택.

선택한 수정 — player-summary.ts:40-41:

const score = entry.scores[event.key]
if (!score || score.status !== 'recorded') continue

buildTrend/buildPersonalBest(player-summary.ts:49-91)는 이미 필터링된 ValidScore[]만 받으므로 전혀 손대지 않는다 — 추이·PB·델타 공식은 그대로 유지된다(완료 조건 그대로 충족).

4작업 단계

  1. 수정: collectValidScores의 entry.scores[event.key] 조회 직후에 !score 가드를 추가한다 — if (!score || score.status !== 'recorded') continue. 함수의 다른 부분(정렬, 반환 타입)은 그대로 둔다. functions/lib/player-summary.ts:40-41 완료 — 계획대로 한 줄 가드만 추가. 임시로 되돌려 확인한 결과, 가드 없이는 player-summary.ts:41에서 정확히 TypeError: Cannot read properties of undefined (reading 'status')로 재현됨(회귀 재현 확인).
  2. 신규 테스트: 기존 최상단 SESSIONS/EVENTS/PLAYERS 픽스처는 완료 조건에 따라 무수정으로 남겨두고, 새 describe 블록에 별도 로컬 픽스처를 추가한다 — (1) 신규 종목: 초반 세션들엔 eventKeys/scores에 해당 key가 아예 없다가 이후 세션부터 등장하는 종목의 시계열 — 이 종목의 첫 유효 기록 포인트가 deltaFromPrevious: null로 나오는지 확인. (2) 종료 종목: endSessionDate가 설정된 이벤트가 초반 세션(종료 전)엔 기록이 있다가, 그 이후 세션들에서는 eventKeys/scores에서 완전히 빠지는 시계열 — 종료 전 기록으로 계산된 trend/PB가 그대로 보존되고, 종료 이후 세션들을 순회해도 크래시 없이 조용히 스킵되는지 확인. 두 케이스 모두 가드 없이는 collectValidScores가 entry.scores[event.key] 접근에서 바로 TypeError를 내는 지점이므로, 수정 전에 실행하면 실패(크래시)해야 정상. functions/lib/player-summary.test.ts 완료 — 계획대로 신규/종료 두 시나리오를 한 픽스처(1회차·2회차=종료종목만, 3회차·4회차=신규종목만)로 결합해 describe('computePlayerSummaries — 미측정 회차 스킵 가드', …)에 추가. 신규 종목 첫 포인트 deltaFromPrevious: null, 종료 종목 이력·PB 보존 두 단언 모두 통과.
  3. 검증: npm test(vitest, 회귀 포함 전체)와 npm run typecheck(tsc -b)를 실행하고, 기존 computePlayerSummaries/경계값 테스트가 무수정으로 그린인지 확인한다. functions/lib/player-summary.test.ts 완료 — npm test: 83개 파일 683개 테스트 전부 통과(기존 픽스처 무수정). npm run typecheck: 0 에러.

5리스크

리스크영향완화책
가드 조건을 score?.status !== 'recorded' 형태로 바꾸면서 실수로 다른 상태(exempt/invalid) 처리 로직까지 건드릴 가능성낮음 — 로직 오회귀 시 기존 면제/이상값 관련 테스트가 즉시 실패해 잡힘변경을 한 줄 가드 추가로 최소화하고, 기존 테스트를 무수정으로 유지해 회귀 감지망으로 사용
새 픽스처가 기존 최상단 SESSIONS/EVENTS를 공유하면 기존 exact-match 단언(toEqual 배열)이 깨질 수 있음중간 — 완료 조건("기존 테스트 무수정 그린")을 못 지킬 수 있음새 시나리오는 별도 describe 블록에 독립된 로컬 이벤트/세션/선수 픽스처로 작성해 기존 블록과 완전히 분리
