1요약

#113·#114·#120이 각각 랭킹·추이·조립 단계에서 종목 생애주기(V4·V6, eventKeys 좁힘)를 구현·단위테스트했지만, 실시트 마이그레이션 후 실제로 벌어지는 상태 — 목표 탭 8행(현역 7 + 종료 1) · 과거 회차 4종목(기록 있음) · 신규 회차 7종목(빈 점수)이 한 번에 섞인 번들 — 을 GET /api/records 라우트 레벨에서 한 번에 검증하는 테스트는 아직 없다. 이 이슈는 docs/prd-event-lifecycle.html §04·§10의 실제 예시 데이터를 그대로 픽스처로 써서 onRequestGet 전 구간(파서→조립→랭킹→추이→홈)의 계약을 한 파일로 못박고, V4·V6 위반 시 500 에러 경로도 같은 라우트에서 함께 검증한다.

2현황 분석

  • 기존 커버리지의 공백 — functions/lib/build-records-response.test.ts:126-160의 "혼재 번들" 테스트는 종목 2개(골밑슛·45도패스캐치)짜리 축소 픽스처로 buildRecordsResponse 함수 하나만 검증한다. functions/api/records.test.ts는 라우트 레벨(캐시·에러 매핑)을 다루지만 종목 1개짜리 최소 픽스처뿐이라 rankings·trends·home이 실제로 어떻게 조립되는지는 보여주지 않는다. 프론트 E2E(src/App.e2e.test.tsx)는 UI 플로우 검증이 목적이라 목 백엔드가 functions/를 아예 import하지 않는다(주석 8-9행) — 실제 파서·조립 코드가 전혀 걸리지 않는다.
  • 목표 데이터 형태 — docs/prd-event-lifecycle.html:159-167 §04가 마이그레이션 후 목표 탭의 정확한 5열 8행을 예시로 못박아 뒀다: 드리블셔틀런·골밑슛·자유투·패스-체스트·패스-바운드·패스-원핸드·볼 캐치(현역 7) + 45도패스캐치(종료 회차 2025-05-16).
  • 회차 데이터 형태 — 같은 문서 docs/prd-event-lifecycle.html:356-383 §10이 실제 회차 두 개의 상태를 진단한다: 2025-05-16은 드리블셔틀런·골밑슛·자유투·45도패스캐치 4열(기록 있음, 45도패스캐치는 값 6·7·면제 혼재), 2026-07-23은 신규 7종목 헤더에 참가자 행은 있지만 점수가 전부 빈칸. scripts/seed-sheet.mjs:44-53의 SESSION_SCORES가 바로 이 2025-05-16 실데이터(선수1~6, 45도패스캐치 값 6·7·7·5·면제·6)라 그대로 재사용 가능하다.
  • 조립 파이프라인 — functions/api/records.ts:15-34의 onRequestGet이 fetchSheetBundle(모킹 대상) → buildRecordsResponse(functions/lib/build-records-response.ts:55-89, 명단·목표 파싱 → 회차별 parseSession → computeSessionRankings → computePlayerSummaries → computeHomeSummary) → JSON 직렬화까지 한 번에 탄다. 이 체인 전체를 도는 것이 라우트 테스트의 장점이고, fetchSheetBundle 모킹 패턴은 functions/api/records.test.ts:5-13에 이미 있다.
  • 검증 매트릭스 위치 — V4(회차 헤더에 종료 종목이 종료일 초과해 존재)는 functions/lib/parse-session.ts:169-179 mapHeaderToEvents가, V6(종료 회차가 실존 회차 탭 이름과 불일치)는 functions/lib/build-records-response.ts:36-45 validateEndSessionDates가 각각 평범한 Error를 던진다. functions/api/records.ts:46-48의 errorResponse는 RecordsAssemblyError가 아닌 일반 Error를 전부 sheet_data_invalid + 500으로 매핑하므로, 두 위반은 API 계약상 같은 모양(상태 코드·에러 코드)으로 나오지만 원인이 다른 검증 단계라 메시지 내용으로 구분해야 한다(functions/api/records.test.ts:124-136에 이미 한 예시가 있음 — 헤더 불일치).
  • eventKeys=0 레코드 상태의 계약 — functions/lib/compute-rankings.ts:71-80 computeSessionRankings는 session.eventKeys에 있는 종목만큼 SessionRankings.events 항목을 만든다(그 종목에 기록이 하나도 없어도 entries: []로 항목 자체는 유지). functions/lib/compute-home-summary.ts:23-32 achievementRates도 같은 규칙을 그대로 물려받아 eligibleCount 0이면 rate 0으로 채운다. 신규 회차가 "빈 점수"인 시나리오는 바로 이 두 규칙이 실제로 맞물리는지 보여주는 지점이다.

3설계

  • 테스트 레벨: 라우트(onRequestGet) — 단위 함수 아님. 이유: 이슈가 요구하는 "/api/records 전 구간" 계약은 buildRecordsResponse 하나가 아니라 fetchSheetBundle부터 JSON 직렬화·에러 매핑까지 실제로 라우트가 도는 경로다. functions/api/records.test.ts와 같은 모킹 패턴(vi.mock('../lib/sheetsApi', ...))을 그대로 쓴다.
  • 새 파일: functions/api/records.e2e.test.ts. 기존 functions/api/records.test.ts에 케이스를 추가하는 대신 분리한다 — 그 파일은 캐시·에러 매핑처럼 작은 단위 픽스처로 충분한 라우트 관심사를 다루고, 이 이슈는 실시트 규모의 큰 픽스처로 전 계약 필드(events·eventKeys·rankings·trends·home)를 훑는 별도 관심사다. 프론트의 src/App.e2e.test.tsx와 같은 *.e2e.test.ts 명명 관례를 백엔드 쪽에도 맞춘다.
  • 픽스처는 실제 마이그레이션 데이터를 그대로 재사용, 새로 창작하지 않는다. 목표 탭은 docs/prd-event-lifecycle.html §04 예시 그대로(8행), 2025-05-16 회차는 scripts/seed-sheet.mjs의 SESSION_SCORES 그대로(선수1~6, 면제 1건 포함) — 문서·시딩 스크립트·테스트 세 곳이 같은 숫자를 가리키게 해서 "실시트 마이그레이션 후 상태와 동일한 시나리오"라는 이슈 요구를 문자 그대로 만족시킨다. 2026-07-23 회차는 같은 6명을 참가자로 두되 7개 헤더 전부 빈칸(§10 진단 그대로) — 정상 경로의 "빈 점수" 분기가 실제로 걸리게 한다.
  • 정상 경로 검증 범위는 대표값 위주, 전수 검산은 하지 않는다. 랭킹 동점 처리·달성 판정의 전 분기는 이미 compute-rankings.test.ts·compute-home-summary.test.ts·player-summary.test.ts가 단위 레벨에서 촘촘히 덮는다. 이 스모크가 새로 증명해야 하는 것은 "그 계산들이 실제 라우트 안에서 올바른 입력을 받아 올바른 자리에 꽂히는가"이므로, 각 계약 필드(events[] 순서·개수, 회차별 eventKeys, 종료 종목의 면제자 랭킹 제외, 신규 7종목 각각의 빈 entries: [], 추이의 스파스 규칙, personalBests가 신규 종목엔 아예 없음, home.latestSession.participantCount === 0·achievementRates 전부 rate 0)마다 대표 assertion 하나씩만 둔다.
  • V4·V6은 같은 라우트에서 별개 케이스로, 메시지로 구분한다. 둘 다 500 + sheet_data_invalid로 같은 모양이 나오므로 상태 코드만 보면 두 검증을 구분한 게 증명되지 않는다 — 각 케이스에서 에러 메시지가 원인 종목명·날짜를 담고 있는지까지 assert해서 "어느 검증 단계가 잡았는지"를 실제로 구분한다.
    • V4 픽스처: 목표·구 회차는 정상 경로와 동일하게 두고, 신규 회차(2026-07-23, 종료일 2025-05-16 초과) 헤더에 45도패스캐치 컬럼을 잘못 추가.
    • V6 픽스처: 회차 탭은 정상 경로와 동일하게 두고(2025-05-16·2026-07-23 둘 다 실존), 목표 탭의 45도패스캐치 종료 회차만 존재하지 않는 날짜(예: 2025-05-01)로 바꿔치기.

4작업 단계

  1. 공용 픽스처 작성 — 목표 탭 8행(§04 예시 그대로), 명단 6행(선수1~6, 전원 활동), 2025-05-16 회차(4열, seed-sheet.mjs SESSION_SCORES 재사용, 면제 1건 포함), 2026-07-23 회차(7열, 전원 빈칸). functions/api/records.test.ts의 vi.mock('../lib/sheetsApi', ...) + fetchSheetBundleMock + makeFakeCache/makeContext 패턴을 그대로 가져와 새 파일 상단에 둔다. functions/api/records.e2e.test.ts
  2. 정상 경로 — events[] 8개가 목표 탭 순서대로(45도패스캐치가 마지막, endSessionDate: '2025-05-16') 나오는지, sessions[] 두 회차의 eventKeys가 각각 4개·7개인지 assert. functions/api/records.e2e.test.ts
  3. 정상 경로 — rankings[0](2025-05-16)의 45도패스캐치 랭킹에 면제자(선수5)가 빠져 있고 나머지 5명이 랭킹에 포함되는지, rankings[1](2026-07-23)의 7개 종목 전부가 entries: []로 항목은 존재하되 비어 있는지 assert — "빈 점수라도 그 회차 측정 종목 슬롯은 사라지지 않는다"는 계약의 핵심 지점. functions/api/records.e2e.test.ts
  4. 정상 경로 — players[]에서 대표 선수 1~2명의 trends가 8개 종목 전부에 대해 존재하는지(신규 종목은 points: []), 면제자의 45도패스캐치 trends가 points: []인지, personalBests에 신규 7종목 중 하나(예: 볼 캐치)가 아예 등장하지 않는지(스파스 규칙) assert. functions/api/records.e2e.test.ts
  5. 정상 경로 — home.latestSession이 2026-07-23·participantCount: 0(전원 미측정 → 미참여)인지, home.achievementRates가 신규 7종목 각각 eligibleCount: 0, achievedCount: 0, rate: 0인지 assert. functions/api/records.e2e.test.ts
  6. V4 위반 경로 — 신규 회차 헤더에 종료된 45도패스캐치 컬럼을 얹은 번들로 onRequestGet 호출 → 500 + error: 'sheet_data_invalid' + 메시지에 "45도패스캐치"·종료 회차 날짜 포함 assert. functions/api/records.e2e.test.ts
  7. V6 위반 경로 — 목표 탭 45도패스캐치의 종료 회차를 실존하지 않는 날짜로 바꾼 번들로 onRequestGet 호출 → 500 + error: 'sheet_data_invalid' + 메시지에 "45도패스캐치"·그 잘못된 날짜 포함 assert. functions/api/records.e2e.test.ts

5리스크

리스크영향완화책
픽스처가 실제 파서 규칙(정규화 NFKC, "-"·빈칸=null 관례 등)과 미묘하게 어긋나면 조용히 다른 값이 조립돼 assertion이 우연히 통과할 위험거짓 양성 — 계약이 실제로 안 지켜져도 그린모든 원시값을 §04·§10·seed-sheet.mjs 원문 그대로 옮기고, 파생값(초 단위·랭킹 순위 등)은 functions/lib/normalize-score.ts·compute-rankings.ts 로직을 직접 손으로 재검산해 주석으로 남긴다
V4·V6 둘 다 sheet_data_invalid/500으로 응답 모양이 같아 한쪽만 통과해도 다른 쪽이 우연히 그린이 될 수 있음검증 공백 은폐메시지 내용(종목명·날짜)까지 assert해 두 케이스가 서로 다른 코드 경로(parse-session.ts vs build-records-response.ts)에서 터졌음을 구분
새 파일이 기존 functions/api/records.test.ts와 목적이 겹쳐 보여 리뷰에서 중복 지적 가능사소 — 리뷰 왕복플랜 §3에 분리 이유(작은 단위 픽스처 vs 실시트 규모 계약 스모크) 명시, PR 본문에도 동일 설명
