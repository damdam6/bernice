P7 — admin/records 쓰기 경로: 비측정 종목 4xx 계약 테스트

damdam6/bernice 브랜치 feat/122-admin-records-4xx-contract-tests ← main 라벨 enhancement 2026-07-27

1요약

POST /api/admin/records의 scores key 집합 검증(validateScoreKeys)이 그 회차 탭 헤더가 아니라 목표 탭 전체 종목을 기준으로 삼고 있어, 회차 헤더에 없는(= 그 회차 비측정) 종목 key를 요청에 포함해도 조용히 무시된 채 200이 반환된다 — mapHeaderToEvents(#112)가 만든 회차별 측정 종목 서브셋을 실제로는 상속하지 못하고 있었다. 반대로 헤더와 정확히 일치하는 올바른 요청(비측정 종목 key를 생략한 요청)은 오히려 "missing" 400으로 거부된다. 이 이슈는 PRD §09가 요구하는 "비측정 종목 key → 4xx" 계약을 코드로 못박고, 종료 회차 경계(당일 포함) 저장이 정상 동작함을 회귀 테스트로 고정한다.

2현황 분석

파이프라인은 functions/api/admin/records.ts:41의 onRequestPost가 맡는다. 실제 호출 순서:

  • 4단계(functions/api/admin/records.ts:74) playerId 해석.
  • 5단계(functions/api/admin/records.ts:78) validateScoreKeys(scores, events) 호출 — events는 parseGoals가 돌려주는 목표 탭 전체 종목(functions/api/admin/records.ts:71)이다. 이 시점엔 아직 회차 탭조차 찾지 않았고 mapHeaderToEvents도 호출 전이다.
  • 7단계(functions/api/admin/records.ts:101)에서야 mapHeaderToEvents(round.values[0], events, round.name)로 그 회차 헤더가 실제로 측정하는 종목(eventColumns)을 구한다 — V3(회차별 종목 서브셋 완화)·V4(종료 경계 검증)는 이미 여기 구현돼 있다(functions/lib/parse-session.ts:140).
  • 9단계(functions/api/admin/records.ts:111) evaluateScores(scores, events)도 다시 목표 탭 전체 events를 쓴다.
  • 쓰기 자체(buildWritePlan, functions/api/admin/records.ts:117)만 eventColumns(그 회차 한정)를 받아 그 열만 쓴다 — 회차별 측정 종목을 정확히 아는 유일한 지점이다.

결과적으로 목표 탭엔 있지만(= validateScoreKeys가 "알고 있는" 종목) 그 회차 헤더엔 없는(= eventColumns엔 없는) 종목 key를 scores에 포함해 요청해도, validateScoreKeys는 그 key를 unknown으로 보지 않고 evaluateScores는 정상적으로 EventScore를 계산해 응답에 담지만, buildWritePlan은 eventColumns에 없는 그 값을 그냥 건너뛴다 — 200 응답이 나가지만 그 값은 시트에 조용히 안 쓰인다. 반대로 그 회차엔 없는 종목 key를 정상적으로 생략한 "헤더와 정확히 일치하는" 요청은 validateScoreKeys가 "missing"으로 400을 던져 거부한다.

functions/lib/record-write.test.ts:142-146의 주석이 정확히 이 공백을 가리키고 있다: "요청 scores에 그 회차 비측정 종목 key가 왔을 때의 엔드포인트 응답 계약은 #122 소관이다." 라이브러리 레벨(mapHeaderToEvents 재사용)은 #112에서 이미 끝났고, 남은 건 엔드포인트(records.ts)가 그 결과를 키 검증에도 실제로 쓰도록 배선하는 일뿐이다.

3설계

선택한 설계: records.ts의 scores key 집합 검증을 회차 헤더 매핑(eventColumns) 이후로 옮기고, validateScoreKeys·evaluateScores 양쪽 모두 목표 탭 전체 events 대신 eventColumns.map(c => c.event)(그 회차가 실제로 측정하는 종목만)를 넘긴다. 두 라이브러리 함수는 이미 "events 배열을 받는 순수 함수"라 시그니처 변경이 필요 없다 — records.ts 호출부가 어떤 종목 목록을 넘기느냐만 바뀐다(#122가 명시한 "코드 변경 최소"와 부합).

판정 순서는 파일 상단 주석이 이미 선언한 "요청 형식(400) → 자원 존재(404) → 값 유효성(400) → 쓰기(502)"를 그대로 따른다. scores key 집합 검증은 이제 "그 회차 탭이 실존"하고 "그 헤더를 매핑"한 뒤에만 의미가 있는 값(회차별 측정 종목)에 의존하므로, 회차 존재(404)·참가자 존재(404) 판정 다음, 기존 값 검증(evaluateScores) 직전 자리로 옮긴다 — 사실 현재 코드는 이 문서화된 순서와 이미 어긋나 있었다(key 검증이 회차 존재 확인보다 먼저 있었다).

반려한 대안:

  • (a) validateScoreKeys 호출부에 별도의 날짜 기준 자체 판정(event.endSessionDate === null || sessionDate <= event.endSessionDate)을 새로 넣는 안 — "규칙 원천은 하나"(mapHeaderToEvents 재사용, PRD §08) 원칙에 반해 같은 판정을 두 곳에 중복 구현하게 되어 기각.
  • (b) buildWritePlan이 eventColumns에 없는 key를 만나면 그 자리에서 에러를 던지게 하는 안 — 쓰기 직전까지 가서야 실패하면 "값 검증(400) → 쓰기(502)" 순서 문서와 어긋나고, invalid 필드처럼 문제를 한 번에 모아 응답하는 기존 관례와도 다름.

5리스크

리스크영향완화책
key 검증 위치를 회차 존재/헤더 매핑 뒤로 옮기면 기존 400/404 순서 테스트가 깨질 수 있다 회귀 기존 makeBundle() 픽스처는 모든 라운드가 목표 탭 전체를 그대로 측정해 eventColumns의 종목 == 목표 탭 전체 종목이므로, 순서를 바꿔도 결과값(400/404 여부·메시지)은 동일 — 기존 스위트 전체 재실행으로 확인
